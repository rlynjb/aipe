2.1 Serverless vs Traditional

Language-Agnostic Concept

Serverless functions (also called Functions-as-a-Service or FaaS) are the idea that you deploy individual functions rather than long-running server processes. The cloud platform manages everything below the function boundary: container provisioning, scaling, networking, and process lifecycle. AWS Lambda, Vercel Edge Functions, Cloudflare Workers, Netlify Functions, and Google Cloud Functions are all variations of this model. The code you write is nearly identical across them; the differences are timeout limits, memory ceilings, and cold-start behaviour.

The fundamental architectural constraint of serverless is statelessness: each function invocation starts with a fresh execution context. There is no shared memory between requests — no global caches, no connection pools, no singleton objects that persist. This forces good design (explicit state management) but creates friction for patterns that assumed statefulness: database connection reuse, in-process caches, and — critically for AI apps — long-running LLM calls that exceed timeout limits.

The cold start problem is specific to serverless: when a function hasn't been invoked recently, the platform must provision a new container, load the runtime, and execute your initialisation code before handling the request. For buffr, this means loading LangChain, registering tools, and initialising SDK clients adds 350–800ms to the first request. Mitigation strategies include keeping bundle size small (lazy imports), avoiding heavy initialisation in the module scope, and using platform-level keep-warm features.

🎯 What are the limitations of serverless for AI applications? ▶
Two main limitations: timeout limits and no persistent state. For timeouts, streaming is the primary solution — start returning tokens immediately so the function doesn't time out waiting. For persistent state you need external storage. A secondary limitation is cold starts — mitigated by keeping bundles small and using dynamic imports so unused SDK code isn't loaded.

2.2 REST API Design Decisions

Language-Agnostic Concept

REST (Representational State Transfer) is an architectural style for HTTP APIs, not a protocol or standard. Its core constraints are: client-server separation, statelessness (each request contains all information needed to process it), uniform interface (resources identified by URLs, manipulated via standard HTTP verbs), and layered system (clients don't know if they're talking to a server or a proxy). REST is language-agnostic — you can implement a RESTful API in TypeScript, Python, Go, Ruby, or anything that can speak HTTP.

The key design decision every API faces is how to structure resource URLs vs operation URLs. Strict REST uses nouns and HTTP verbs: GET /sessions lists, POST /sessions creates, DELETE /sessions/:id removes. In practice, especially for serverless where each file is a function, many teams use a hybrid: one file per resource, query params to differentiate operations (?summarise, ?review). This is what buffr does — pragmatic for solo development, but worth understanding the trade-off before scaling a team.

Schema validation (Zod in TypeScript, Pydantic in Python, Joi in Node, Marshmallow in Python, express-validator in Express) is not optional in production. The pattern is always: parse and validate at the boundary, work with typed/validated data inside, and return structured errors to clients. Never use raw request data inside business logic. This prevents entire classes of bugs — type coercion issues, missing field crashes, and injection vectors.

buffr uses "one file per resource, query params for sub-operations." Understanding why — and when it breaks down — is the mark of an engineer who thinks in systems.

2.3 Storage Patterns & Race Conditions

Language-Agnostic Concept

Every application needs to store data. The choice of storage pattern is independent of language — the same trade-offs apply whether you're in Node, Python, Go, or Ruby. Key-value stores (Redis, DynamoDB, Netlify Blobs, Cloudflare KV) map a string key to an arbitrary value blob. They're fast for single-record access but have no query capability — you can't ask "give me all sessions from last week" without fetching everything and filtering in application code. Relational databases (Postgres, MySQL, SQLite) add SQL, indexes, joins, and transactions — the ability to query across records efficiently. Document stores (MongoDB, Firestore) are a middle ground: schema-flexible, queryable, but without full relational power.

The TOCTOU race condition (Time Of Check To Time Of Use) is a concurrency bug that appears in any language when two operations read a shared resource, each makes a decision based on what they read, and then both write back — with one overwriting the other's changes. It's not a JavaScript problem; it's a general concurrent programming problem. In databases, this is solved with transactions and row-level locking. In serverless blob storage (which has no transactions), you must either serialise operations or use atomic compare-and-swap operations where available.

An index pattern is the practice of maintaining a separate data structure that tracks which keys belong to a logical set — essentially a poor-man's database index. When you store sessions:list:projectId as a key that holds an array of session IDs, you're implementing a manual index so you don't have to scan all sessions to find those for a project. This pattern is a pragmatic bridge between key-value stores and relational databases — use it until query complexity justifies migrating to Postgres.

PatternWhat it isWhen to use
Key-value storeSimple map of key → JSON blobPrototypes, per-user config, small datasets < 1000 items
Relational (Postgres)Tables, indexes, SQL queries, joinsWhen you need to filter/sort/search across records

Two key patterns: one-blob-per-record (prompts, dev-items, sessions) — each item independent, listing requires fetching all. One-blob-per-project-as-collection (manual-actions, action-notes) — faster to list, but concurrent writes can hit the TOCTOU bug.

The TOCTOU race condition — a real bug encountered in buffr:

BROKEN (Promise.all):
  Delete A: read [A,B,C] → remove A → write [B,C]
  Delete B: read [A,B,C] → remove B → write [A,C]  ← stale read!
  Result: A is back. Last write wins.

FIXED (sequential):
  Delete A: read [A,B,C] → remove A → write [B,C]
  Delete B: read [B,C]   → remove B → write [C]    ← reads fresh state

🎯 When would you migrate buffr from Netlify Blobs to Postgres? ▶
When queries become the bottleneck — filtering sessions by date range, searching prompt text, or joining sessions with project data. The tell-tale sign is list-and-filter-in-memory becoming visibly slow, usually around 500–1000 records. I'd migrate to Supabase Postgres, add an index on projectId and createdAt, and keep the storage module interface unchanged so chain code doesn't need to change.
