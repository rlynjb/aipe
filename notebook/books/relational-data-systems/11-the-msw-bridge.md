## Chapter 11 — The msw bridge: `toHandlers` — collections become an API

This is the part that makes it `@mswjs/data` and not just an in-memory ORM. Each model converts itself into **msw request handlers**.

```js
import { setupServer } from 'msw/node'

const server = setupServer(
  ...db.user.toHandlers('rest'),   // generates GET/POST/PUT/DELETE for /users
  ...db.post.toHandlers('rest'),   // ...and for /posts
)
```

```
   what toHandlers('rest') generates — every route is just a
   CRUD operation from Part III wired to an HTTP verb:

   ┌────────────────────────┬─────────────────────────┬──────────────┐
   │ HTTP REQUEST           │ @mswjs/data OPERATION   │ BOOK CHAPTER │
   ├────────────────────────┼─────────────────────────┼──────────────┤
   │ GET    /users          │ db.user.findMany()      │ Ch 5 pipeline│
   │ GET    /users/:id      │ db.user.findFirst({id}) │ Ch 5.1 lookup│
   │ POST   /users  + body  │ db.user.create(body)    │ Ch 6.1 create│
```

**Wiring the todo API end-to-end.** Imagine your todo-app component code expects a normal REST backend at `/todos`. You haven't written that backend yet — but you don't have to. Hook `toHandlers` into msw and the frontend can't tell the difference:

```js
import { setupServer } from 'msw/node'

const server = setupServer(
  ...db.user.toHandlers('rest', 'http://api.test'),
  ...db.list.toHandlers('rest', 'http://api.test'),
  ...db.todo.toHandlers('rest', 'http://api.test'),
  ...db.tag.toHandlers('rest',  'http://api.test'),
)

server.listen()
```

Now the component code can call `fetch('http://api.test/todos')` and it just works. The handlers msw registered are the ones `toHandlers` synthesised by reading the schema — and what they do internally is hit the same `db.todo.findMany()` machinery from Chapter 9.

```
   ┌─ todo app UI ─┐    GET /todos          ┌─ msw handler ─┐
   │ const data =  │ ────────────────────►  │ generated by  │
   │   await fetch │                        │ toHandlers    │
   │   ('/todos')  │                        └───────┬───────┘
   └───────────────┘                                │
        ▲                                           │ calls
        │ JSON: [{id, text, done, ...}]             ▼
        │                                  ┌─────────────────┐
        │                                  │ db.todo         │
        │                                  │   .findMany()   │
        │                                  └────────┬────────┘
        │                                           │
        │                                           ▼
        │                                  ┌─────────────────┐
        │                                  │ todo Map        │
        │                                  │ (Chapter 2)     │
        │                                  └────────┬────────┘
        │                                           │
        └──────── JSON response ◄──────── records ──┘
```

Two layers were synthesised mechanically: the *HTTP handlers* (from the schema), and the *records assembled with joins* (from the collection storage). You wrote neither. You wrote the schema in Chapter 7, seeded with `create` in Chapter 8, and now you have a fully working REST API for tests, storybooks, and offline-first development.

**The pattern stretches beyond mocks.** `toHandlers` is the most concrete example of a deep idea: *if you have a schema, you can synthesise the entire CRUD surface mechanically.* That's what frameworks like Hasura, PostgREST, and Prisma Studio do — they take a schema and generate a REST or GraphQL API on top of it, no per-endpoint code required. Once you understand that the schema *contains enough information to generate the API*, you stop writing controllers by hand for boring CRUD.

```
   schema in                       what gets generated
   ──────────────                  ──────────────────────────────
   user collection                 GET    /users        (findMany)
   primaryKey id                   GET    /users/:id    (findFirst)
   3 value fields                  POST   /users        (create)
   1 oneOf reference               PUT    /users/:id    (update)
                                   DELETE /users/:id    (delete)

   …same five endpoints generated for list, todo, tag.
   schema with 4 collections → 20 routes, none written by hand.
```

This is the payoff of the whole book. Once you can see "schema → operations → API" as one continuous mechanical pipeline, you understand what every relational tool — from `@mswjs/data` up to Postgres + Prisma + tRPC in production — is doing under the hood. They differ in *durability* (in-memory vs disk) and *strictness* (mock vs full integrity), but the pipeline is the same.
