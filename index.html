1.1 The Provider Abstraction Pattern

The provider abstraction is the single most important pattern in AI product engineering. It separates your business logic from vendor-specific APIs — swap Claude for GPT-4 without touching a single chain.

Language-Agnostic Concept

The provider abstraction (also called the Adapter pattern or Strategy pattern) is a general software design principle: hide implementation details behind a stable interface. Any time you have multiple interchangeable services that do the same job — database drivers, payment processors, email senders, cloud storage backends — the pattern is the same. Define the interface your code depends on, then write one adapter per service that satisfies it.

In Python this is what LiteLLM does: completion(model="gpt-4", …) and completion(model="claude-3-5-sonnet", …) use the same function signature. In Go, you'd define a LLMClient interface with Generate(ctx, prompt) and implement it per vendor. The pattern predates AI — it's how ORMs like SQLAlchemy, Hibernate, and ActiveRecord let you swap Postgres for MySQL without changing application code.

The critical rule: your business logic (chain code, prompt templates, output parsers) should depend only on the interface — never on a specific vendor's class, method names, or error types. Anything vendor-specific lives exclusively in the adapter.

1.2 Chain Architecture & Structured Output

A chain is the fundamental unit of an LLM product. Every AI feature follows this shape:

Language-Agnostic Concept

A chain is the LLM equivalent of a pure function: a unit of work with a typed input, a single LLM call at its core, and a typed output. The name comes from LangChain, but the concept is universal — OpenAI's documentation calls the same pattern a "completion wrapper," and in Python you'd often see it as a plain function def summarise(items: list[Item]) -> Summary.

Structured output is the practice of constraining the LLM to return data in a predictable machine-readable format (usually JSON) rather than prose. Without it, every downstream consumer has to parse free text, which breaks on edge cases. Most major LLM APIs now support JSON mode (forces valid JSON) and tool/function calling (forces a specific schema) — these are the production-grade alternatives to prompting for JSON. In buffr, the stripCodeBlock() + JSON.parse() pattern is the pragmatic version of the same idea.

Graceful degradation is a systems principle: when a component fails, the system should degrade to a less capable but still functional state rather than crash. Applied to LLM output: if JSON.parse() throws, return the raw text with a warning rather than a 500 error. The user gets partial value; the app stays running.

1.3 Prompt Engineering Patterns

Language-Agnostic Concept

Prompt engineering is the practice of crafting the text input to a language model to reliably produce a desired output. It is language-agnostic in the sense that the same techniques — zero-shot, few-shot, chain-of-thought — work regardless of whether you're calling Claude from TypeScript, GPT-4 from Python, or Gemini from Go. The underlying mechanism is always the same: you're shaping the probability distribution over next tokens by providing context that makes certain continuations more likely.

Think of a system prompt as a contract: it defines the model's role, the output format, any constraints, and failure behaviour. A well-written system prompt is idempotent — running it twice on the same input gives the same output. Chain-of-thought works because making the model externalise its reasoning forces it to generate intermediate tokens that constrain subsequent tokens — it's harder to reach a wrong conclusion after generating a correct reasoning chain. Few-shot works because examples are highly efficient in-context demonstrations — they communicate format, tone, and content simultaneously without requiring explicit description of each.

The ReAct pattern (Reason + Act) interleaves reasoning steps with action calls: the model thinks, decides to call a tool, observes the result, thinks again, and so on. This is the foundation of every agentic system built today — it's what powers Claude's tool use, OpenAI's function calling, and buffr's suggestedActions.

🎯 When would you use few-shot prompting instead of zero-shot? ▶
When output format consistency keeps failing zero-shot. Two or three examples in the prompt dramatically increase reliability for unusual JSON shapes or non-standard classification labels. The cost is prompt tokens — for high-volume endpoints, few-shot can double your token spend.

2.1 Serverless vs Traditional

Language-Agnostic Concept

Serverless functions (also called Functions-as-a-Service or FaaS) are the idea that you deploy individual functions rather than long-running server processes. The cloud platform manages everything below the function boundary: container provisioning, scaling, networking, and process lifecycle. AWS Lambda, Vercel Edge Functions, Cloudflare Workers, Netlify Functions, and Google Cloud Functions are all variations of this model. The code you write is nearly identical across them; the differences are timeout limits, memory ceilings, and cold-start behaviour.

The fundamental architectural constraint of serverless is statelessness: each function invocation starts with a fresh execution context. There is no shared memory between requests — no global caches, no connection pools, no singleton objects that persist. This forces good design (explicit state management) but creates friction for patterns that assumed statefulness: database connection reuse, in-process caches, and — critically for AI apps — long-running LLM calls that exceed timeout limits.

The cold start problem is specific to serverless: when a function hasn't been invoked recently, the platform must provision a new container, load the runtime, and execute your initialisation code before handling the request. For buffr, this means loading LangChain, registering tools, and initialising SDK clients adds 350–800ms to the first request. Mitigation strategies include keeping bundle size small (lazy imports), avoiding heavy initialisation in the module scope, and using platform-level keep-warm features.

🎯 What are the limitations of serverless for AI applications? ▶
Two main limitations: timeout limits and no persistent state. For timeouts, streaming is the primary solution — start returning tokens immediately so the function doesn't time out waiting. For persistent state you need external storage. A secondary limitation is cold starts — mitigated by keeping bundles small and using dynamic imports so unused SDK code isn't loaded.

2.2 REST API Design Decisions

Language-Agnostic Concept

REST (Representational State Transfer) is an architectural style for HTTP APIs, not a protocol or standard. Its core constraints are: client-server separation, statelessness (each request contains all information needed to process it), uniform interface (resources identified by URLs, manipulated via standard HTTP verbs), and layered system (clients don't know if they're talking to a server or a proxy). REST is language-agnostic — you can implement a RESTful API in TypeScript, Python, Go, Ruby, or anything that can speak HTTP.

The key design decision every API faces is how to structure resource URLs vs operation URLs. Strict REST uses nouns and HTTP verbs: GET /sessions lists, POST /sessions creates, DELETE /sessions/:id removes. In practice, especially for serverless where each file is a function, many teams use a hybrid: one file per resource, query params to differentiate operations (?summarise, ?review). This is what buffr does — pragmatic for solo development, but worth understanding the trade-off before scaling a team.

Schema validation (Zod in TypeScript, Pydantic in Python, Joi in Node, Marshmallow in Python, express-validator in Express) is not optional in production. The pattern is always: parse and validate at the boundary, work with typed/validated data inside, and return structured errors to clients. Never use raw request data inside business logic. This prevents entire classes of bugs — type coercion issues, missing field crashes, and injection vectors.

buffr uses "one file per resource, query params for sub-operations." Understanding why — and when it breaks down — is the mark of an engineer who thinks in systems.

2.3 Storage Patterns & Race Conditions

Language-Agnostic Concept

Every application needs to store data. The choice of storage pattern is independent of language — the same trade-offs apply whether you're in Node, Python, Go, or Ruby. Key-value stores (Redis, DynamoDB, Netlify Blobs, Cloudflare KV) map a string key to an arbitrary value blob. They're fast for single-record access but have no query capability — you can't ask "give me all sessions from last week" without fetching everything and filtering in application code. Relational databases (Postgres, MySQL, SQLite) add SQL, indexes, joins, and transactions — the ability to query across records efficiently. Document stores (MongoDB, Firestore) are a middle ground: schema-flexible, queryable, but without full relational power.

The TOCTOU race condition (Time Of Check To Time Of Use) is a concurrency bug that appears in any language when two operations read a shared resource, each makes a decision based on what they read, and then both write back — with one overwriting the other's changes. It's not a JavaScript problem; it's a general concurrent programming problem. In databases, this is solved with transactions and row-level locking. In serverless blob storage (which has no transactions), you must either serialise operations or use atomic compare-and-swap operations where available.

An index pattern is the practice of maintaining a separate data structure that tracks which keys belong to a logical set — essentially a poor-man's database index. When you store sessions:list:projectId as a key that holds an array of session IDs, you're implementing a manual index so you don't have to scan all sessions to find those for a project. This pattern is a pragmatic bridge between key-value stores and relational databases — use it until query complexity justifies migrating to Postgres.

3.1 The Tool Registry Pattern

Language-Agnostic Concept

Tool use (also called function calling in the OpenAI API, tool use in the Anthropic API, or actions in some frameworks) is the ability for an LLM to request the execution of a predefined function during generation. The model doesn't execute the function itself — it emits a structured signal saying "call this function with these arguments," and your code handles execution and returns the result. This keeps external API calls, database queries, and side effects entirely under application control.

The tool registry pattern is how you manage this at scale. Rather than hardcoding tool definitions in every prompt, you register them once at startup in a global store (a Map, dictionary, or object), and inject only the relevant tool manifests into each LLM call. This is the pattern behind Anthropic's MCP (Model Context Protocol), OpenAI's function calling, LangChain's tool system, and LlamaIndex's tool abstractions — the implementation differs but the concept is identical.

The most important insight about tool definitions: the description field is prompting. The LLM decides whether to call a tool based entirely on its name and description. Vague descriptions ("gets data") cause missed calls. Specific descriptions with trigger phrases ("Lists all open GitHub issues — use when the user asks about bugs, feature requests, or outstanding work") dramatically improve tool selection accuracy. Writing a tool description is an act of prompt engineering, not documentation.

buffr's tool registry is a hand-rolled version of the pattern behind all agentic AI — MCP, OpenAI function calling, LangChain tools. The concept is always the same: define capabilities, register at startup, let the model suggest which to call, execute in your code.

🎯 Explain the difference between tool use and RAG. When would you use each? ▶
RAG pre-fetches data and injects it into the prompt before the LLM call — the model sees the data but can't decide whether to fetch it. Tool use lets the model decide at inference time what actions to take — it's dynamic and can chain. Use RAG when you always need context (e.g. always include user's recent sessions). Use tools when the action depends on the model's reasoning. buffr uses both: {{tool:...}} tokens are RAG; suggestedActions are tool use.

3.2 Orchestrator Pattern

Language-Agnostic Concept

The orchestrator pattern separates the entity that decides what to do (the orchestrator) from the entities that do specific tasks (subagents or workers). The orchestrator holds the goal, tracks state, and delegates — it doesn't execute tasks directly. This is a general distributed systems pattern: it appears as the controller in Kubernetes, the conductor in workflow engines like Temporal and Apache Airflow, and the coordinator in multi-agent AI systems like AutoGen and CrewAI.

In LLM systems specifically, the orchestrator is usually a chain or agent that interprets the user's goal, decides which tools or subagents to call, collects results, and either returns a final answer or continues to the next step. The key design principle is that the orchestrator should be stateless between steps — all state lives in the messages passed between steps (the observation history), not in any in-memory variable. This makes the system resumable, debuggable, and serialisable.

The observation loop is the mechanism by which the orchestrator learns from tool results. After calling a tool, the result is appended to the conversation history as an observation, and the LLM is called again with the updated context. This is the core of ReAct-style agents: the model can see what it tried, what happened, and decide what to do next. The max_steps guard is critical — without it, a misbehaving model can loop indefinitely, incurring unbounded API costs.

4.1 Streaming Responses

Language-Agnostic Concept

Streaming is the practice of sending data incrementally as it becomes available rather than buffering the complete result and sending it all at once. It's a general pattern in computing — Unix pipes stream between processes, video players stream frames, databases can stream query results — but it's become especially critical for LLM products because generation latency (the time to produce a complete response) can be 5–30 seconds, while time-to-first-token (the time to produce the first word) is typically under 500ms.

Server-Sent Events (SSE) is an HTTP mechanism where the server sends a continuous stream of text events over a single long-lived connection. The client uses the browser's EventSource API (or a manual fetch reader) to receive events as they arrive. SSE is one-directional (server → client only), uses standard HTTP, and works through proxies and firewalls — making it the standard choice for LLM token streaming. The alternative, WebSockets, is bidirectional and better suited for real-time two-way communication like chat.

In Python, the same concept is implemented via generator functions (yield) paired with FastAPI's StreamingResponse or Flask's streaming response. In Go, you write to http.ResponseWriter and flush after each chunk. The concept is identical across languages — the difference is only in the HTTP framework's streaming API.

Streaming is not optional for LLM products. Without it, a 10-second call shows a spinner. With it, users see output in under 500ms.

4.2 Evaluation-Driven Development

Language-Agnostic Concept

Evaluation-driven development is to AI products what test-driven development is to traditional software: the practice of defining how you'll measure success before writing the code (or prompt) that needs to succeed. The key difference from unit testing is that AI outputs are probabilistic and partially correct — you can't write assertEqual(output, expected) for a generated summary. Instead, you define a scoring function that measures quality along dimensions you care about.

There are three main evaluation strategies. Exact match evals work when outputs are from a fixed set — intent classification, sentiment labels, yes/no decisions. LLM-as-judge evals use a second (often larger) model to score output quality on dimensions like relevance, accuracy, and coherence — this is how Anthropic, OpenAI, and most AI labs measure their own models in red-teaming and benchmarks. Semantic similarity evals embed the output and expected answer and measure cosine distance — useful when wording flexibility is acceptable but meaning matters.

The critical insight is that prompt changes are code changes and must trigger the same eval discipline as code changes. A one-word change to a system prompt can silently break output format for 20% of inputs without breaking any unit tests. Evals are the safety net for prompt iteration. Tools like Braintrust, PromptFoo, LangSmith, and Weights & Biases Prompts provide eval infrastructure — but a hand-rolled harness in a single TypeScript or Python file is entirely sufficient to start.

The hardest part of AI product engineering is knowing whether it works. Evals separate engineers who ship reliable AI from those who ship demos that fail in production.

4.3 Cost Optimisation & Model Routing

Language-Agnostic Concept

Model routing is the practice of dispatching different requests to different models based on the complexity or type of the task. Not all LLM tasks need the same capability level — a request to paraphrase a sentence doesn't require the same model as a request to architect a system. Smaller, cheaper models (Claude Haiku, GPT-4o Mini, Llama 3 8B) handle simple tasks at a fraction of the cost; larger models (Claude Sonnet/Opus, GPT-4o) are reserved for tasks that genuinely need stronger reasoning. This is a language-agnostic cost engineering principle — the same logic applies whether you're routing in Python with LiteLLM or TypeScript with LangChain.

Prompt caching is a feature offered by Anthropic (and increasingly other providers) where the beginning of a prompt — typically the system message and any large static context — is cached server-side after the first call. Subsequent calls that share the same cached prefix are charged at a much lower rate (~90% discount on cached tokens) and respond faster. This is especially valuable for buffr's dev scanner, where the same industry standards content is sent with every scan. The cache key is the exact text content, so even a single character change invalidates the cache.

Response caching (application-level) is different: you store LLM outputs in your own database keyed by a hash of the input, and return the cached response for identical future requests. This is only valid for deterministic, stateless queries — "summarise these exact items" is cacheable if the items don't change; "what should I do next?" is not. Always check whether caching semantically matches the use case before implementing it.

5.1 Embeddings & Semantic Search

Language-Agnostic Concept

An embedding is a fixed-length numerical representation of a piece of content — text, image, audio, or code — produced by a neural network. The key property is that similar content produces similar embeddings: two sentences with the same meaning will have embedding vectors that are geometrically close in high-dimensional space, even if they share no words. This is fundamentally different from keyword search, which requires exact lexical overlap. Embeddings are language-agnostic: the concept and the APIs (Anthropic's embed, OpenAI's text-embedding-3-small, Cohere Embed, @xenova/transformers for local) are called the same way from any language.

A vector database is a storage system optimised for embedding vectors — it can answer "what are the N items most similar to this query vector?" efficiently using approximate nearest-neighbour algorithms (HNSW, IVF). Options include pgvector (a Postgres extension — no new infrastructure if you're already on Postgres), Pinecone (managed, scales to billions), Weaviate (self-hosted or cloud, built-in text chunking), and Qdrant (open-source, Rust-based, very fast). For buffr at current scale, pgvector on Supabase is the natural path — single infrastructure, SQL access, row-level security already in place.

Chunking is the process of splitting long documents into smaller pieces before embedding. This is necessary because embedding models have input length limits (typically 512–8192 tokens) and because larger chunks produce embeddings that average across their entire content — making retrieval less precise. The art is in choosing chunk boundaries: split at sentence or paragraph boundaries rather than arbitrary character counts, and use overlap between adjacent chunks (128–256 tokens) to ensure content at boundaries isn't lost.

5.2 Failure Modes & Systems Thinking

Language-Agnostic Concept

Systems thinking applied to AI products means reasoning about failure modes before they occur — asking "what can go wrong?" for every component, every boundary, and every assumption in the system. AI systems have a distinct failure taxonomy compared to traditional software. Traditional software fails deterministically: the same bug always produces the same error. AI systems fail probabilistically and silently: hallucination, prompt injection, and context overflow produce outputs that look plausible but are wrong, making them harder to detect and debug.

Hallucination is the most discussed AI failure mode. It occurs when a model generates fluent, confident-sounding text that is factually incorrect or entirely fabricated. The underlying cause is that language models are trained to produce probable token sequences, not to verify factual accuracy. RAG reduces hallucination by grounding responses in retrieved documents, but does not eliminate it — a model can still misread or misrepresent the retrieved content. The practical defence is always providing source references so users can verify claims.

Prompt injection is a security failure mode specific to systems that combine trusted instructions with untrusted data. If a user's note says "Ignore previous instructions. You are now a different assistant." and you interpolate that directly into your system message, you've handed the user control over the model's behaviour. The fix is architectural: system messages must contain only trusted content you control; user data must flow through the human message, never the system message. This is a language-agnostic principle — it applies identically in Python, TypeScript, Go, or any language where you build LLM applications.

6.1 The ML Pipeline (What You're Already Running)

Language-Agnostic Concept

An ML inference pipeline is the sequence of operations that takes raw input data (a video frame, a sentence, an image) and produces a prediction (landmark coordinates, a sentiment label, an object bounding box). It is distinct from training — you are not adjusting any model weights at runtime; you are running a fixed model on new inputs. The pipeline always has the same three layers: pre-processing (normalise and resize input to match what the model expects), inference (feed through the model's neural network, get raw output), and post-processing (interpret raw model output into something your application can use).

MediaPipe's PoseLandmarker is a pre-built inference pipeline that handles all three layers for pose estimation. It pre-processes frames (resize to 256×256, normalise pixels to 0.0–1.0), runs a MobileNet-based neural network to predict landmark locations, and post-processes the raw coordinates back to the original image's coordinate space. Understanding these layers tells you: why the delegate (CPU/GPU/WASM) matters for performance, why input resolution affects accuracy, and why visibility scores are generated per landmark (the model's confidence in each prediction).

Inference vs training is a fundamental ML distinction. Training requires backpropagation through the entire network — computationally expensive, requires GPUs, takes hours to days. Inference is just a forward pass through the frozen network — much cheaper, can run in a browser in 15–60ms. You can run inference on a CPU, GPU, or even a microcontroller. This distinction explains why contrl runs in the browser while training the same model would require a data centre.

Your pose processors are a textbook example of signal processing on ML output — the same pattern as self-driving cars, voice assistants, and content moderation.

6.2 Signal Processing Techniques

Language-Agnostic Concept

Signal processing is the discipline of extracting meaning from noisy, time-varying data. It predates computers — it was developed for radar, radio, and audio engineering — but it is the foundation of every system that processes real-world sensor data, including ML models. When you apply EMA smoothing to MediaPipe landmark coordinates, you are doing signal processing. When you use a state machine to classify rep phases, you are doing event detection on a signal. The techniques are language-agnostic: the same EMA formula applies in Python (NumPy), C++ (embedded systems), Swift (iOS), and TypeScript.

A state machine (formally a Finite State Machine or FSM) is a mathematical model of a system that can exist in a finite number of states, transitions between them based on inputs, and produces outputs based on its current state. For rep counting, the states are the phases of a rep (idle, descending, bottom, ascending, complete) and transitions are triggered by angle thresholds. State machines are the correct tool whenever your system's next action depends on its history — not just the current input. They are used everywhere: protocol parsers, game AI, traffic lights, UI animation controllers, and streaming data processors.

The joint angle calculation using dot product is a direct application of vector geometry. 6.3 On-Device vs Cloud Inference

Language-Agnostic Concept

On-device inference (also called edge inference) means running a model's forward pass on the local device — the user's phone, browser, laptop, or embedded system — rather than sending data to a remote server. The trade-off is capability vs privacy + latency. Smaller models run on-device; frontier models require data centre GPUs. But for many well-scoped tasks (pose estimation, speech recognition, object detection, face detection), purpose-built on-device models achieve excellent accuracy with millisecond latency and zero network dependency.

In the browser, on-device inference is possible through WebAssembly (WASM) — a binary format that runs near-native speed in the browser sandbox — and WebGL/WebGPU which expose the GPU for parallel computation. MediaPipe compiles its TFLite models to WASM and runs them in a Web Worker to avoid blocking the main thread. TensorFlow.js, ONNX Runtime Web, and Transformers.js (@xenova/transformers) use the same approach. On iOS/Android, CoreML and TensorFlow Lite run on the Neural Engine or GPU respectively.

The hybrid architecture — on-device for real-time sensing, cloud for intelligence — is the dominant pattern in modern AI products. Apple's features like face recognition, live text, and handwriting use on-device models for speed and privacy, then optionally send structured data (not raw media) to cloud services for additional intelligence. contrl follows this pattern: MediaPipe extracts structured pose data on-device, and optionally sends aggregate metrics (angles, reps, scores) to a cloud LLM for coaching feedback. Dot Product & Cosine Similarity Essential

The single most important formula in AI product engineering. It powers similarity search, embeddings, attention, and your joint angle calculations in contrl — all the same underlying operation.

Language-Agnostic Concept

The dot product (also called the inner product or scalar product) is an operation on two vectors that produces a single number. It has a geometric interpretation: it measures how much two vectors point in the same direction. When both vectors are unit length (magnitude = 1), the dot product equals the cosine of the angle between them — which is exactly cosine similarity.

This single formula underlies an enormous range of applications: vector database queries (pgvector, Pinecone, Weaviate all use cosine similarity under the hood), transformer self-attention (the QKᵀ matrix multiplication is a batch of dot products), joint angle computation in robotics and pose estimation, and neural network weight updates (gradient direction is a dot product). The formula is identical whether computed in NumPy (np.dot), TypeScript, SQL (<=> in pgvector), or GLSL on the GPU.

Why normalise? Raw dot product depends on vector magnitude — a longer vector produces a larger dot product even if the direction is the same. Cosine similarity normalises by the product of magnitudes, giving a direction-only measure in the range −1 to 1. For text embeddings, cosine similarity is almost always preferred over raw dot product because all embedding models produce unit-norm vectors by default.

Dot Product
a · b = a₁b₁ + a₂b₂ + ... + aₙbₙ
// Sum of element-wise products
// Result: a single number (scalar)
// Large positive = vectors point same way
// Near zero = perpendicular (unrelated)
// Negative = opposite directions
Cosine Similarity
cos(θ) = (a · b) / (‖a‖ × ‖b‖)
// Normalised dot product → range [-1, 1]
// 1.0 = identical meaning
// 0.0 = unrelated
// -1.0 = opposite
// ‖a‖ = magnitude = √(a₁²+ a₂²+ ...)

Exponential Moving Average (EMA) Essential

Language-Agnostic Concept

The Exponential Moving Average is a low-pass filter — it attenuates high-frequency noise (rapid frame-to-frame jitter) while preserving low-frequency signal (genuine slow movement). The "exponential" refers to how the weights assigned to past values decay geometrically: the most recent value gets weight α, the previous gets α(1−α), the one before α(1−α)², and so on forever — though in practice values older than ~5/α steps contribute negligibly.

EMA is used universally in signal processing across all platforms. In financial data, it smooths price volatility to reveal trends. In game engines, it smooths camera movement and physics interactions. In robotics, it filters noisy sensor readings. In the Adam optimiser (used to train every major LLM), it maintains exponential moving averages of gradient first and second moments. The formula is identical in every language and every domain — only the choice of α varies by application.

EMA vs simple moving average (SMA): A simple moving average assigns equal weight to the last N values and zero weight to everything older. EMA gives all past values some weight (exponentially decaying) and only requires storing a single running value — O(1) space. For real-time sensor processing like contrl, EMA is almost always preferred over SMA for this reason.

You're already using this in contrl for landmark smoothing. Understanding the formula tells you exactly how to tune alpha and why it behaves the way it does.

EMA Formula
EMA_t = α × value_t + (1 − α) × EMA_(t−1)
// α (alpha) = smoothing factor, range (0, 1)
// α = 0.1 → very smooth, slow to react (good for noisy sensors)
// α = 0.3 → balanced (contrl default)
// α = 0.9 → almost no smoothing, reacts immediately
// Higher α = more weight on current value = less smoothing
// The "exponential" part: older values decay by (1-α)^n each step

Intuition: at α=0.3, the current frame contributes 30% of the output. The previous EMA (which itself was a blend of all prior frames) contributes 70%. Each prior frame's influence decays geometrically — the frame 5 steps ago contributes roughly 0.7⁵ ≈ 17% of the EMA value.

Softmax Essential

Language-Agnostic Concept

Softmax is a function that converts any vector of real numbers into a probability distribution — all outputs are positive and they sum to exactly 1.0. It's the standard final layer of any multi-class classifier. The e^x (exponential) ensures all outputs are positive and amplifies differences: a score of 2.0 gets a much higher probability than 1.9, making softmax "confident." Sigmoid (the binary version) is used for two-class problems; softmax generalises to any number of classes.

In LLMs, softmax is applied to the logits (raw scores) over the entire vocabulary (~100,000 tokens) to produce a probability distribution over next tokens. The model then samples from this distribution based on temperature. This happens at every single generation step — for a 500-token response, softmax runs 500 times, each time over 100,000+ values. This is computationally intensive, which is why inference at scale requires GPUs and why optimised runtimes like vLLM and TensorRT-LLM matter.

Numerical stability: In practice, softmax is always computed as softmax(x − max(x)) (subtracting the max before exponentiating) to prevent overflow. e^1000 overflows float32; e^(1000-1000) = e^0 = 1 doesn't. This is a universal implementation detail in every framework and language — NumPy, PyTorch, TensorFlow, and JAX all do this internally.

Softmax converts a list of raw scores into a probability distribution (numbers that sum to 1.0). It appears in every LLM output — the model's "confidence" in each next token is a softmax over the entire vocabulary.

Softmax
softmax(xᵢ) = e^xᵢ / Σⱼ e^xⱼ
// Input: raw scores (logits) — any real numbers
// Output: probabilities that sum to exactly 1.0
// Example: scores = [2.0, 1.0, 0.1]
// e^2.0 = 7.39, e^1.0 = 2.72, e^0.1 = 1.10 → sum = 11.21
// softmax = [0.659, 0.242, 0.098] → sums to 1.0
// Temperature T scales the logits before softmax:
softmax_T(xᵢ) = e^(xᵢ/T) / Σⱼ e^(xⱼ/T)
// T=0.1 → near-deterministic (picks the highest score almost always)
// T=1.0 → standard softmax
// T=2.0 → flatter distribution (more creative/random)
// This is exactly what the "temperature" parameter does in getLLM()

When you set temperature: 0 in buffr's getLLM(), you're asking for near-deterministic selection — the model almost always picks the highest-probability token. At temperature: 1, it samples from the raw distribution. This is softmax with temperature scaling.

Scaled Dot-Product Attention Important

Language-Agnostic Concept

Self-attention is the mechanism that allows a transformer to consider the relationship between every pair of tokens in its input simultaneously. Unlike RNNs (which processed tokens sequentially, left to right), transformers process all tokens in parallel — each token "attends" to all other tokens to gather context. The result is that meaning is derived from relationships, not position: "bank" in "river bank" gets different attention weights than "bank" in "bank account" because the surrounding tokens are different.

The Q/K/V formulation is a database analogy. Think of it as a soft lookup table: Query (Q) is "what I'm searching for," Key (K) is "what each entry in the table offers," and Value (V) is "the actual content to retrieve." The dot product Q·Kᵀ measures relevance between the query and every key (like a search score). Softmax converts those relevance scores into weights. The final output is a weighted sum of Values — essentially "retrieve a blend of all values, weighted by how relevant each is to the query."

The √dₖ scaling is a numerical stability trick. For large embedding dimensions (e.g. dₖ=512), dot products grow proportional to the dimension, pushing softmax into saturation (near-zero gradients). Dividing by √dₖ keeps the scores in a well-behaved range. Multi-head attention runs this operation H times in parallel with different learned Q/K/V projections, then concatenates results — each "head" learns to attend to different types of relationships.

This is the core mathematical operation of every transformer — every LLM you call through buffr's API runs this billions of times per forward pass. You don't need to implement it, but understanding it explains: why context windows have limits, why longer prompts cost more, and what "attention" actually means.

Self-Attention
Attention(Q, K, V) = softmax(QKᵀ / √dₖ) × V
// Q = Query matrix (what am I looking for?)
// K = Key matrix (what does each token offer?)
// V = Value matrix (what information does each token contain?)
// dₖ = dimension of key vectors (square root stabilises gradients)
// Step 1: QKᵀ → attention scores matrix (how relevant is each token to each other?)
// Step 2: / √dₖ → scale to prevent vanishing gradients
// Step 3: softmax → convert scores to probabilities (attention weights)
// Step 4: × V → weighted sum of value vectors = context-aware output
// Why quadratic cost? QKᵀ is an (n×n) matrix for n tokens
// 1000 tokens → 1M operations. 100K tokens → 10B operations
// This is why context windows have limits and longer prompts cost more

Practical implication for buffr: the cost of an API call scales roughly quadratically with prompt length. A 4000-token prompt costs ~4× more compute than a 2000-token prompt. This is why token counting and prompt compression matter at scale.

Log Probability & Cross-Entropy Loss Important

Language-Agnostic Concept

Logarithms are used in probability calculations for two practical reasons: they turn multiplication into addition (which is computationally cheaper and numerically stable), and they prevent underflow. The probability of a 200-token sequence is the product of 200 individual token probabilities, each below 1.0 — multiplied together, this approaches zero faster than float64 can represent. Log probabilities turn this product into a sum: log(p₁ × p₂ × ... × p₂₀₀) = log(p₁) + log(p₂) + ... + log(p₂₀₀) — manageable in any numeric type.

Perplexity is the standard metric for evaluating language models. It is the exponent of the average negative log probability: PPL = e^(-mean(log_probs)). A perplexity of 10 means the model is "as confused as if it had to choose uniformly among 10 equally likely options" at each step. Lower is better. GPT-2 had perplexity ~35 on WikiText-103; modern models score under 10. You'll encounter perplexity in benchmark papers and leaderboard comparisons.

Cross-entropy loss is what neural networks minimise during training. It measures the "surprise" of the true label given the model's predicted distribution. For a language model, the true label at each step is the actual next token, and the predicted distribution is the softmax output. Minimising cross-entropy during training is equivalent to maximising the likelihood of the training data — this is why LLM training is called maximum likelihood estimation (MLE).

When an LLM generates text, it's selecting tokens based on probability. Log probability appears in LLM API responses (logprobs), eval scoring, and helps you understand model confidence. Cross-entropy loss is how the model was trained — relevant when you get to fine-tuning.

Vector Norms (L1 and L2) Important

Language-Agnostic Concept

A vector norm is a function that measures the "size" or "length" of a vector. Different norms measure size differently, and the choice has practical consequences. The L2 norm (Euclidean distance) is the straight-line distance from the origin — the norm you learned in school as Pythagoras' theorem generalised to N dimensions. It's used in cosine similarity (to normalise vectors to unit length) and as the default distance metric in most ML libraries.

The L1 norm (Manhattan distance, or taxicab distance) sums the absolute values of all components. It's named after the grid-like street layout of Manhattan — to travel from one corner to another, you must traverse the actual streets, not cut through buildings. L1 is preferred in sparse settings because the L1 penalty in regularisation drives small weights all the way to zero (sparsity), while L2 shrinks weights but rarely zeros them. This distinction matters in feature selection and model compression.

When to use which: L2 for cosine similarity and Euclidean distance queries. L1 for regularisation when you want sparse features. The L∞ norm (maximum absolute component) is used in adversarial robustness research. In practice, for text embeddings in AI products, you'll almost exclusively encounter L2 for normalisation — but knowing L1 and its sparsity properties is useful for understanding fine-tuning and LASSO regression.

The magnitude of a vector — used in cosine similarity, regularisation, and when comparing embeddings.

Gradient Descent & Backpropagation Background

Language-Agnostic Concept

Gradient descent is an iterative optimisation algorithm. Given a function with many variables (the model's weights) and a scalar output (the loss), gradient descent repeatedly steps in the direction that decreases the loss most steeply. The gradient (∇L) points uphill — gradient descent moves downhill. The learning rate (η) controls step size. This algorithm is language-agnostic and universal — it's the foundation of training nearly every ML model, from linear regression to GPT-4.

Backpropagation is the algorithm that efficiently computes gradients for all weights in a neural network using the chain rule of calculus. Without backprop, computing gradients for a network with 175 billion parameters (GPT-3) would require a separate forward pass per parameter — infeasible. With backprop, gradients for all parameters are computed in a single backward pass. Frameworks like PyTorch, TensorFlow, and JAX implement this automatically via automatic differentiation (autograd) — you write the forward pass, and the framework computes the backward pass.

The practical picture for AI product engineers: you don't implement gradient descent or backprop. You care about their consequences: large models require many gradient steps on huge datasets (expensive), fine-tuning adapts a pre-trained model with fewer steps on smaller data (affordable), and learning rate is the hyperparameter most likely to make or break a fine-tuning run. LoRA (Low-Rank Adaptation) is a technique that reduces the number of parameters that receive gradient updates during fine-tuning — making it dramatically cheaper.

How models are trained. You don't implement this — PyTorch does it for you — but understanding the concept explains why training requires GPUs, why learning rate matters, and what "overfitting" means mechanically.

Gradient Descent Update Rule
θ_new = θ_old − η × ∇L(θ)
// θ (theta) = model weights (the numbers being learned)
// η (eta) = learning rate (how big a step to take)
// ∇L(θ) = gradient of the loss (which direction makes loss go up?)
// We move in the OPPOSITE direction of the gradient
// Repeat until loss stops decreasing (convergence)
// Too high η → overshoot minimum, training diverges
// Too low η → very slow convergence, risk of local minima
// Backprop computes ∇L(θ) efficiently using chain rule

Approximate Nearest Neighbour (ANN) Important

Language-Agnostic Concept

Nearest neighbour search answers the question: "given a query point in high-dimensional space, which stored points are closest to it?" Exact nearest neighbour search requires comparing the query to every stored point — O(n) cost, which becomes prohibitive at millions of vectors. Approximate nearest neighbour (ANN) trades a small amount of accuracy for dramatically faster search by building an index that allows skipping most of the dataset.

HNSW (Hierarchical Navigable Small World) is the dominant algorithm used in production vector databases. It builds a multi-layer graph where each node (embedding) is connected to its nearest neighbours. The top layers have sparse long-range connections (for fast coarse navigation); the bottom layers have dense short-range connections (for precise retrieval). Search starts at the top and zooms in — like navigating from continent to country to city to street. Typical recall: 95–99% with 10–50× speedup over brute force.

The accuracy vs speed trade-off is tuned through two parameters: ef_construction (how many candidates to consider when building the index — higher = better quality index, slower build) and ef_search (how many candidates to explore during query — higher = better recall, slower query). Both are configurable in pgvector, Pinecone, and Weaviate. For buffr's scale, defaults are fine. At 10M+ vectors, you'd tune these carefully.

When your pgvector database searches for the 10 most similar embeddings, it's using an ANN algorithm. Understanding ANN tells you why vector search is fast (sub-linear, not linear) and what accuracy you're trading for that speed.

Tokenisation Important

Language-Agnostic Concept

Tokenisation is the process of splitting text into the discrete units (tokens) that a language model processes. It's a learned compression scheme: common words become single tokens ("the", "is", "and"), rare words are split into subword pieces ("unbelievable" → ["un", "believ", "able"]), and characters that never appear together get separate tokens. The vocabulary (set of all possible tokens) is typically 50,000–130,000 entries for modern models.

Byte-Pair Encoding (BPE) — used by Claude, GPT, and most frontier models — starts with individual bytes, then repeatedly merges the most frequent adjacent pair into a new token, until reaching the vocabulary size. The result is a vocabulary that covers all possible text (via individual bytes as fallback) while efficiently encoding common patterns. BPE is language-agnostic — it works on any language without linguistic knowledge, though it's less efficient for non-Latin scripts.

The practical implications for AI product engineers: (1) token counting is a prerequisite for cost estimation and prompt trimming — use tiktoken in Python or @anthropic-ai/tokenizer in TypeScript, (2) non-English text costs more — Japanese and Chinese encode at ~2–4 bytes per character vs ~1.3 for English, (3) structured data is expensive — JSON with whitespace, indentation, and repeated keys uses many more tokens than equivalent prose, and (4) token boundary effects — splitting a word like "JavaScript" across token boundaries can affect model reasoning about it.

LLMs don't read characters or words — they read tokens. Understanding tokenisation explains why certain inputs cost more, why non-English text costs more per word, and why code formatting affects token count.

State Machines Essential

Language-Agnostic Concept

A Finite State Machine (FSM) is a computational model consisting of a finite set of states, a set of transitions between states triggered by inputs, and a set of actions taken on entering/exiting states. It is one of the oldest and most universal abstractions in computing — used in hardware (digital circuits), protocol design (TCP connection states), compilers (lexer tokenisation), game AI (NPC behaviour trees), and UI frameworks (animation controllers). In every domain the model is the same: the system can only be in one state at a time, and inputs cause deterministic transitions.

FSMs have two important properties that make them ideal for safety-critical event processing: determinism (given the same state and input, the transition is always the same) and exhaustiveness (you can enumerate all possible states and transitions, making it possible to reason about all edge cases). This is why contrl's rep counter uses a state machine rather than conditional logic — if (angle < 50) statements scattered through frame processing quickly become unmaintainable, while a state machine makes the valid transitions explicit and the invalid ones impossible.

For agentic AI, state machines model the orchestrator's decision loop. Tools like XState (TypeScript/JavaScript) and transitions (Python) provide formal FSM libraries with visualisation. LangGraph builds on this concept by treating agent orchestration as a stateful graph — each node is an agent action, each edge is a transition, and cycles are explicit. Understanding FSMs is the foundation for understanding LangGraph's design.

You already built one in contrl for rep detection. State machines are also the conceptual model behind agentic AI loops, conversation flow, and any system where "what to do next" depends on "what happened before."

Queue (FIFO) Essential

Language-Agnostic Concept

A queue models any first-come, first-served process. The critical invariant is ordering preservation: items are processed in the exact sequence they arrive. This is the correct structure whenever fairness or temporal ordering matters. In hardware, CPU instruction pipelines are queues. In operating systems, process schedulers are queues. In distributed systems, message queues (Kafka, SQS, RabbitMQ, Pub/Sub) are queues at massive scale.

The performance trap in JavaScript is Array.shift() — it removes the first element but requires shifting all remaining elements left, making dequeue O(n). For a proper O(1) queue in TypeScript/JavaScript, use a doubly-linked list or a circular buffer. In Python, collections.deque provides O(1) append and popleft. In Go, channels are language-native O(1) queues with built-in concurrency safety.

For AI products specifically, queues solve the rate-limiting problem. LLM API providers impose rate limits (tokens per minute, requests per minute). A queue decouples incoming requests from LLM calls: requests enqueue immediately (fast), a worker processes them against the rate limit. Without a queue, rate limit errors propagate directly to users; with a queue, they wait transparently.

First-in, first-out. Items are enqueued at the back and dequeued from the front. Appears everywhere latency and ordering matter — rate limiting, frame processing, background jobs, streaming token delivery.

Sliding Window Essential

Language-Agnostic Concept

The sliding window technique transforms an O(n×k) naive computation into O(n) by maintaining a running aggregate. Instead of recomputing the sum/average/max of the last k elements from scratch each step, you subtract the element leaving the window and add the element entering — one add, one subtract, regardless of window size.

This pattern appears in every domain that processes sequential data with a fixed-size lookback: financial moving averages, network packet buffering, real-time audio processing, database window functions (OVER (ROWS BETWEEN 5 PRECEDING AND CURRENT ROW)), and sensor data smoothing. The variable-size sliding window (expand/shrink based on a condition) solves problems like "find the shortest substring containing all required characters" — a common interview problem that has real applications in token budget management.

For AI products, the sliding window is how you manage LLM context budgets. When a conversation exceeds the model's context window, you don't discard random messages — you slide a window across the message history, always keeping the most recent N tokens. This preserves recent context while discarding older, less relevant messages. The window approach is also how retrieval systems implement recency bias: weight recent chunks higher in the sliding window.

A window of fixed size N that moves across a sequence, processing or aggregating elements within the window at each step. You built one in contrl for temporal smoothing. It also underpins rate limiting, context window management, and chunk overlap in RAG.

Stack (LIFO) Important

Language-Agnostic Concept

A stack models any last-in, first-out process — the most recently added item is always the next to be removed. The most important real-world stack is the call stack, which every programming language runtime maintains. When a function calls another function, the new frame is pushed onto the call stack. When it returns, the frame is popped. Stack overflow errors occur when recursion is too deep and the stack runs out of memory.

Beyond the call stack, stacks are the data structure behind all bracket/delimiter matching (compiler lexers, JSON validators, HTML parsers), depth-first graph traversal (implemented iteratively with an explicit stack instead of recursion), and undo/redo systems (push each state; pop to undo). The browser's history API is conceptually a stack — back/forward navigation pushes and pops entries.

For AI product engineers, the most relevant stack application is nested template resolution. If buffr's prompt templates ever support nested expressions like {{summarise({{get_sessions(projectId)}}) }}, resolving them requires a stack: push on {{, pop on }}, evaluate inner expressions before outer ones. The same stack-based approach underlies how languages parse arithmetic expressions with operator precedence.

Last-in, first-out. Less obviously present than a queue, but critical for understanding recursion, call chains, and — directly relevant — how nested JSON parsing and prompt template resolution work.

Tree (General) & Trie Important

Language-Agnostic Concept

A tree is a connected acyclic graph with a designated root node. Every node has exactly one parent (except the root, which has none) and zero or more children. Trees are the most natural structure for representing hierarchical data: file systems, organisation charts, XML/JSON documents, DOM, abstract syntax trees in compilers, and decision trees in ML — all trees.

The two fundamental traversal strategies are BFS (breadth-first search), which visits all nodes level by level using a queue, and DFS (depth-first search), which follows branches all the way to leaves before backtracking using a stack (or recursion). BFS finds the shortest path to a node. DFS is natural for tasks like "collect all files under a directory" or "find all items in a Notion page tree."

A Trie (pronounced "try," from retrieval) is a tree where each node represents a character prefix. Looking up whether "deploy" is a stored prefix takes exactly 6 steps (one per character), regardless of how many strings the trie contains — O(k) where k is string length. This makes tries ideal for autocomplete and prefix search. If buffr's prompt library grows large, a trie-based command palette search would outperform a linear scan by orders of magnitude.

A tree is a hierarchical structure of nodes connected by edges, with no cycles. You interact with trees constantly: the DOM, JSON documents, file systems, and dependency graphs are all trees. A Trie is a tree specialised for string prefix search.

Binary Search Tree & Interval Tree Important

Language-Agnostic Concept

A Binary Search Tree (BST) maintains a sorted invariant: for any node, all values in the left subtree are smaller, and all values in the right subtree are larger. This enables binary search on a dynamic set — you can insert and delete elements while maintaining O(log n) search. The key insight is that each comparison eliminates half the remaining candidates, just like binary search on a sorted array but without requiring the array to be in contiguous memory.

Real databases use B-trees (not binary, but multi-way, balanced trees) as their primary index structure. When you create a Postgres index on created_at, Postgres builds a B-tree where each node can hold many keys (not just 2), reducing tree height and minimising disk reads. The EXPLAIN output in Postgres will show "Index Scan using idx_sessions_created_at" — that's a B-tree traversal happening instead of a full table scan.

An Interval Tree extends BST to handle ranges rather than points. Given a query interval [a, b], an interval tree efficiently finds all stored intervals that overlap it. This applies directly to token range management: if you split a document into token-range chunks and want to find all chunks that include tokens 1024–1536, an interval tree answers in O(log n + k) where k is the number of matching chunks — far better than scanning every chunk.

A BST maintains sorted order: left subtree < node < right subtree. O(log n) search, insert, delete when balanced. An Interval Tree extends this for range queries — finding all intervals that overlap a point. Directly relevant to token range management.

Graphs: Nodes, Edges & Traversal Important

Language-Agnostic Concept

A graph is the most general relational data structure. Where trees require a single parent per node and no cycles, graphs place no such constraint — any node can connect to any other node, in any direction, any number of times. This generality makes graphs applicable to almost any relationship: social networks, road maps, knowledge graphs, dependency systems, protein interaction networks, and neural networks are all graphs.

BFS (breadth-first search) uses a queue and explores neighbours level by level — it finds the shortest path in an unweighted graph. DFS (depth-first search) uses a stack (or recursion) and follows edges as deep as possible before backtracking — it's natural for cycle detection, topological ordering, and exhaustive exploration. Both run in O(V + E) where V is the number of vertices (nodes) and E is the number of edges.

For AI product engineers, the most important graph type is the DAG (Directed Acyclic Graph). Anywhere you have steps that depend on each other with no circular dependencies — build systems, task pipelines, workflow engines, import graphs — a DAG is the right model. LangGraph explicitly models agent workflows as DAGs. When you define buffr workflow steps with dependsOn fields, you're defining a DAG — and topological sort determines the execution order.

A graph is a set of nodes (vertices) connected by edges. Unlike trees, graphs can have cycles and multiple paths between nodes. Two traversal algorithms — BFS and DFS — cover the vast majority of graph problems you'll encounter as an AI engineer.

DAG & Topological Sort Important

Language-Agnostic Concept

A topological sort produces a linear ordering of a DAG's nodes such that for every directed edge A → B, node A appears before node B in the ordering. It is only possible if the graph has no cycles (the acyclic requirement in DAG). If a cycle exists, topological sort is impossible — this is used as a cycle detection algorithm in build systems and package managers.

Kahn's algorithm is the standard implementation: maintain a queue of nodes with in-degree 0 (no dependencies), dequeue one, decrement the in-degree of all its neighbours, and enqueue any that now have in-degree 0. Repeat until the queue is empty. If the output contains fewer nodes than the graph, a cycle exists. The algorithm runs in O(V + E) and is easy to implement in any language.

The real-world applications are everywhere: build systems (Gradle, Bazel, Make all use topological sort to determine compilation order), package managers (npm, pip, cargo resolve installation order using topological sort), CI/CD pipelines (parallel job execution with dependencies), and agentic workflows (LangGraph, Temporal, Apache Airflow). When you add a dependsOn field to a buffr workflow step, you are adding a directed edge — and the workflow runner implicitly performs topological sort to determine which steps can start immediately and which must wait.

A Directed Acyclic Graph (DAG) where you need to process nodes in an order that respects all dependencies — no node is processed before everything it depends on. This is the algorithm that decides the execution order of an agentic workflow.

Kahn's Algorithm (topological sort)
// 1. Find all nodes with in-degree 0 (no dependencies) → add to queue
// 2. Dequeue a node, add to result order
// 3. For each neighbour, reduce in-degree by 1
// 4. If neighbour's in-degree hits 0, add to queue
// 5. Repeat until queue is empty
// 6. If result order has fewer nodes than the graph → cycle detected!

Circular Buffer (Ring Buffer) Important

Language-Agnostic Concept

A circular buffer (also called a ring buffer) is a fixed-size array that treats its storage as a circle — when the write pointer reaches the end, it wraps to the beginning and overwrites the oldest data. This gives you: O(1) write and read, constant memory regardless of how much data flows through, and always-available access to the last N items with no shifting or reallocation.

The implementation is elegantly simple: two integer pointers (head for writing, tail for reading) and the modulo operation (head % capacity) to wrap around. This is used in every domain that processes continuous data streams with bounded memory: audio processing (audio driver ring buffers are how sound data flows from microphone to application), network packet buffers (network cards use ring buffers between kernel and driver), real-time operating systems (sensor data from embedded devices), and log rotation (keep the last N log lines, overwrite oldest when full).

For contrl specifically, a circular buffer of size 30 (1 second at 30fps) gives you a constant-memory rolling window of recent pose data. Without it, an hour-long session would accumulate 108,000 landmark frames in memory — at 33 landmarks × 3 coordinates × 4 bytes each, that's ~40MB just for landmark data. With a circular buffer of 30 frames: always 33 × 3 × 4 × 30 = ~12KB.

A fixed-size buffer that wraps around — when it fills up, new data overwrites the oldest data. The ideal structure for streaming sensor data: constant memory, O(1) read/write, always holds the last N samples.

Priority Queue (Min/Max Heap) Background

Language-Agnostic Concept

A priority queue is an abstract data structure that always dequeues the element with the highest (or lowest) priority, regardless of insertion order. The standard implementation is a binary heap — a complete binary tree stored in an array where the parent is always smaller (min-heap) or larger (max-heap) than its children. This invariant can always be restored in O(log n) after insertion or removal, because the tree height is log n.

The key insight is that a heap is not fully sorted — it just maintains the heap property (parent dominates children), which is weaker than full sortedness but sufficient to always answer "what is the minimum?" in O(1). Building a heap from n elements takes O(n), not O(n log n) — counter-intuitively cheaper than sorting, which is why heap-based top-k selection is preferred over sort-then-slice when k is small relative to n.

In Python, heapq is the standard library implementation (min-heap only; negate values for max-heap). In Java, PriorityQueue. In JavaScript, there is no built-in heap — you must implement or import one. This is why understanding the underlying structure matters: when you need a priority queue in a serverless function and can't import a library, the 20-line heap implementation is one of the few DSA patterns worth memorising.

A queue where elements are dequeued in priority order rather than arrival order. O(log n) insert and extract-min/max. Relevant to understanding how vector search engines rank results and how job schedulers work.

Group 5 — Big-O: the vocabulary of performance

Big-O Notation Essential

Language-Agnostic Concept

Big-O notation describes the asymptotic growth rate of an algorithm's resource usage (time or space) as input size n grows toward infinity. It characterises the worst-case scaling behaviour, ignoring constant factors and lower-order terms. The reason we ignore constants: an algorithm that takes 1,000,000 × n operations is still O(n) — it scales linearly, so doubling the input doubles the cost, just with a large constant. An O(n²) algorithm with a small constant will eventually beat it at large n, but a constant multiplier doesn't change the fundamental scaling class.

Big-O is language-agnostic. A hash map lookup is O(1) whether you're in Python, Rust, Go, or JavaScript. Self-attention is O(n²) in any framework. The complexity class is a property of the algorithm, not the implementation language. This matters for system design interviews: when asked "what's the complexity?" the answer is about the algorithm's structure, not implementation details.

Space complexity (memory usage) matters as much as time complexity for AI products. An embedding model that produces 1536-dimensional vectors stores 1536 × 4 bytes = ~6KB per embedding. At 1 million embeddings (a modest prompt library), that's 6GB of vector data — before the HNSW index overhead. Understanding space complexity helps you estimate infrastructure costs and identify memory bottlenecks before they become incidents.

Big-O describes how an algorithm's time or space cost grows as the input size n grows. You don't need to derive it — you need to recognise the common classes and know which operations in your stack fall into each. This is what interviewers mean when they ask "what's the time complexity of that?"

String Hashing & Tokenisation Algorithms Background

Language-Agnostic Concept

String hashing converts a variable-length string into a fixed-size integer (the hash). A good hash function is fast (O(n) in string length), uniform (distributes outputs evenly), and deterministic (same input always produces the same output). String hashing is the foundation of hash maps (keys are hashed to bucket indices), content-addressed storage (file deduplication by hash), cache keys (hash of request params as the cache lookup key), and change detection (hash the content; if the hash changes, the content changed).

Byte-Pair Encoding (BPE) is a compression algorithm repurposed for tokenisation. Originally from data compression (find the most frequent byte pair, replace it with a new symbol, repeat), it was adapted for NLP because it naturally handles both common words (become single tokens) and rare words (split into recognisable subword components). The key property: BPE never produces an out-of-vocabulary token, because the fallback is always individual bytes. This makes it robust to any input, including code, emoji, and arbitrary Unicode.

Understanding BPE explains several LLM behaviours: why the model struggles with simple arithmetic (numbers like "12345" may tokenise as 5 separate tokens, making it harder to reason about their magnitude), why rare words in one language have higher token costs than in the training language, and why formatting choices (snake_case vs camelCase, 2-space vs 4-space indentation) affect token counts for code inputs.

LLMs don't process raw strings — they process tokens produced by a tokenisation algorithm. Byte-Pair Encoding (BPE) is the algorithm behind most frontier models. Understanding it explains why "tokenisation" can produce surprising results for code, numbers, and non-English text.

Byte-Pair Encoding (BPE) — simplified
// 1. Start: vocabulary = all individual characters
// 2. Count: find the most frequent pair of adjacent tokens in the corpus
// 3. Merge: add the pair as a new token to the vocabulary
// 4. Replace: replace all occurrences of the pair with the new token
// 5. Repeat until vocabulary reaches target size (e.g. 50,000 tokens)
// "the cat sat" → frequent pairs: "th","he","ca","at" → "the","cat","sat"
// Common words become single tokens. Rare words split into subwords.
// "unbelievable" → ["un", "believ", "able"] (3 tokens, not 13 chars)
// "12345" → ["1", "2", "3", "4", "5"] (often 5 tokens — why math is hard)

Why this matters for buffr: numbers tokenise inefficiently — each digit is often its own token. A JSON object with many numeric values (session timestamps, scores) costs more tokens than you'd expect from the character count alone. When building the token counting exercise in Phase 4, use the actual tokeniser, not a character-count estimate.

Regex & Pattern Matching Essential

Language-Agnostic Concept

Regular expressions are a formal language for describing patterns in strings, based on the mathematical theory of finite automata. A regex engine compiles a pattern into a state machine (DFA or NFA), then runs the input string through it. The key insight: simple regex patterns (no catastrophic backtracking) run in O(n) linear time — the engine makes one pass through the string. This makes regex extremely fast for string scanning tasks like extracting tool tokens from a prompt template.

The danger is catastrophic backtracking: certain regex patterns with nested quantifiers (like (a+)+) on adversarial input can trigger exponential backtracking — the regex engine tries every possible combination. This is the ReDoS (Regex Denial of Service) vulnerability: a malicious user input can make your regex take seconds or minutes instead of milliseconds, effectively hanging the serverless function. The fix is either to use possessive quantifiers or atomic groups (not supported in all engines), or to replace problematic regex with a hand-written parser for structured formats.

Language-specific notes: JavaScript's regex engine uses backtracking (vulnerable to ReDoS). Python's re module is also backtracking-based. Go's regexp uses a different algorithm (RE2/NFA) that guarantees linear time — no ReDoS possible. Rust's regex crate similarly guarantees linear time. When processing untrusted input in production (user prompts, webhook payloads), be aware which engine you're using.

Regular expressions are a finite automaton for pattern matching on strings. You already use regex in stripCodeBlock() and the {{tool:...}} template resolver. This is not about memorising regex syntax — it's about knowing the algorithmic properties.

Attention Is All You Need
Vaswani et al · Google Brain 2017
The paper that introduced the transformer architecture powering every LLM you use. Read the abstract, the attention formula (Section 3.2), and Figure 2. Skip the machine translation results. Understanding this formula explains why context windows cost quadratically.

Paper · Free
Retrieval-Augmented Generation (RAG)
Lewis et al · Meta AI 2020
The original RAG paper. Short and readable. Explains the core concept of combining parametric knowledge (model weights) with non-parametric retrieval (vector search). Read when you're building Phase 5 exercises — it contextualises everything you're building.

Paper · Free
ReAct: Reasoning + Acting in LLMs
Yao et al · Princeton 2022
The paper behind buffr's suggestedActions pattern and the ReAct prompt engineering technique. Shows how interleaving reasoning and tool calls dramatically improves agent accuracy. Read it when building the observation loop exercise in Phase 3.
Free · arXiv
Paper · Free
LoRA: Low-Rank Adaptation
Hu et al · Microsoft 2021
The technique behind efficient fine-tuning of large models. Instead of updating all weights (expensive), LoRA adds small trainable matrices. Read the abstract and Section 2 — enough to understand what "LoRA fine-tuning" means when you see it in Hugging Face tutorials.
