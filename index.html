1.1 The Provider Abstraction Pattern

The provider abstraction is the single most important pattern in AI product engineering. It separates your business logic from vendor-specific APIs — swap Claude for GPT-4 without touching a single chain.

ConceptDefinition
Factory functionReturns a configured LLM client without the caller knowing which vendor is underneath
Interface / contractThe caller only knows invoke() and stream(), not ChatAnthropic vs ChatOpenAI
Dynamic dispatchAt runtime the factory picks the implementation based on the provider string from the request body
Lazy loadingrequire() not import — unused SDK bundles aren't loaded, reducing cold start time
LiteLLMPython equivalent of getLLM() — one function, 100+ providers

🎯 Why did you abstract your LLM provider instead of calling the Anthropic SDK directly? ▶
Because locking business logic to a vendor is a design smell. With a factory function, you can add a new provider in one place, A/B test models without touching chains, and fall back gracefully if a provider is down — without modifying the code that actually does work.

1.3 Prompt Engineering Patterns

PatternWhen to use
Zero-shotInstruction only, no examples. Works for simple well-defined tasks. Fast to iterate.

🎯 When would you use few-shot prompting instead of zero-shot? ▶
When output format consistency keeps failing zero-shot. Two or three examples in the prompt dramatically increase reliability for unusual JSON shapes or non-standard classification labels. The cost is prompt tokens — for high-volume endpoints, few-shot can double your token spend.

🎯 What are the limitations of serverless for AI applications? ▶
Two main limitations: timeout limits and no persistent state. For timeouts, streaming is the primary solution — start returning tokens immediately so the function doesn't time out waiting. For persistent state you need external storage. A secondary limitation is cold starts — mitigated by keeping bundles small and using dynamic imports so unused SDK code isn't loaded.

2.2 REST API Design Decisions

buffr uses "one file per resource, query params for sub-operations." Understanding why — and when it breaks down — is the mark of an engineer who thinks in systems.

DecisionTrade-off
One file per resourceSimplifies deployment. Gets messy when a resource has 10+ operations.
Query params for sub-opsAllows sharing provider resolution + error handling. Non-RESTful but practical for serverless.
Manual if(!field) validationSimple and readable. Doesn't scale — use Zod when you have 5+ required fields.
classifyError()Maps vendor-specific LLM error strings to standard HTTP codes. Essential.

2.3 Storage Patterns & Race Conditions

The TOCTOU race condition — a real bug encountered in buffr:

BROKEN (Promise.all):
  Delete A: read [A,B,C] → remove A → write [B,C]
  Delete B: read [A,B,C] → remove B → write [A,C]  ← stale read!
  Result: A is back. Last write wins.

FIXED (sequential):
  Delete A: read [A,B,C] → remove A → write [B,C]
  Delete B: read [B,C]   → remove B → write [C]    ← reads fresh state
TOCTOU — Timeline of the Race Condition
  T (ms)  deleteA thread               deleteB thread            Blob store
    ──────  ─────────────────────────   ──────────────────────   ──────────────
    0     read()  ◀────────────────────────────────────────────── [A, B, C]
    0                                  read()  ◀─────────────────── [A, B, C]
    1     filter([A,B,C], A) = [B,C]
    1                                  filter([A,B,C], B) = [A,C]
    2     write([B,C])  ────────────────────────────────────────▶  [B, C]  ✓
    3                                  write([A,C])  ─────────────▶  [A, C]  ✗
          (deleteA's write is overwritten — A is back)

    ──────────────────────────────────────────────────────────────────────────
    FIXED: sequential for...of

    0     read()  ◀────────────────────────────────────────────── [A, B, C]
    2     write([B,C])  ────────────────────────────────────────▶  [B, C]
    3                                  read()  ◀─────────────────── [B, C]  ← fresh
    5                                  write([C])  ───────────────▶  [C]     ✓
🎯 When would you migrate buffr from Netlify Blobs to Postgres? ▶
When queries become the bottleneck — filtering sessions by date range, searching prompt text, or joining sessions with project data. The tell-tale sign is list-and-filter-in-memory becoming visibly slow, usually around 500–1000 records. I'd migrate to Supabase Postgres, add an index on projectId and createdAt, and keep the storage module interface unchanged so chain code doesn't need to change.

3.1 The Tool Registry Pattern

buffr's tool registry is a hand-rolled version of the pattern behind all agentic AI — MCP, OpenAI function calling, LangChain tools. The concept is always the same: define capabilities, register at startup, let the model suggest which to call, execute in your code.

ConceptHow it works in buffr
Tool definitionname, description, inputSchema (JSON Schema), execute function. The description is what the LLM reads to decide whether to call it.
Tool registryA global Map populated at cold start. O(1) lookup by name. New tools registered via registerTool() — the router doesn't change.
suggestedActionsLLM-suggested tool names + inputs. Your backend validates and executes them.
Server-side executionStage 2 {{tool:...}} resolution runs server-side. GitHub tokens never reach the browser.
MCP equivalenceAnthropic's MCP formalises this exact pattern. buffr's registry could be wrapped as an MCP server with minimal changes.

🎯 Explain the difference between tool use and RAG. When would you use each? ▶
RAG pre-fetches data and injects it into the prompt before the LLM call — the model sees the data but can't decide whether to fetch it. Tool use lets the model decide at inference time what actions to take — it's dynamic and can chain. Use RAG when you always need context (e.g. always include user's recent sessions). Use tools when the action depends on the model's reasoning. buffr uses both: {{tool:...}} tokens are RAG; suggestedActions are tool use.

4.1 Streaming Responses

Streaming is not optional for LLM products. Without it, a 10-second call shows a spinner. With it, users see output in under 500ms.

ConceptWhat it means
Server-Sent EventsOne-directional HTTP stream. Each chunk is a text/event-stream message. Native browser support via EventSource.
Token streamingLLM APIs return tokens one by one as generated. buffr currently waits for full response.
Chunked transferHTTP response body sent in chunks without Content-Length. Connection stays open until stream ends.
BackpressureWhen client can't consume chunks as fast as server produces them. Rarely a problem with LLMs.

🎯 How do you know if your AI feature is working correctly? ▶
You need evals. For each chain, I maintain a test set of input/expected output pairs. For structured output chains, I check exact JSON shape. For generative chains, I use an LLM judge prompt that scores the output on relevance, accuracy, and format adherence 1–5, flagging anything below 4. I run evals on every prompt change, not just code changes, because prompt engineering is code.

Dot Product & Cosine Similarity Essential

The single most important formula in AI product engineering. It powers similarity search, embeddings, attention, and your joint angle calculations in contrl — all the same underlying operation.

Dot Product
a · b = a₁b₁ + a₂b₂ + ... + aₙbₙ
// Sum of element-wise products
// Result: a single number (scalar)
// Large positive = vectors point same way
// Near zero = perpendicular (unrelated)
// Negative = opposite directions
Cosine Similarity
cos(θ) = (a · b) / (‖a‖ × ‖b‖)
// Normalised dot product → range [-1, 1]
// 1.0 = identical meaning
// 0.0 = unrelated
// -1.0 = opposite
// ‖a‖ = magnitude = √(a₁²+ a₂²+ ...)
Where it appearsWhat it's doing
contrl joint anglesDot product of two bone vectors → angle at a joint. The Math.acos(dot/mag) in your exercise code IS this formula.
Vector database queryWhen you do ORDER BY embedding <=> query_embedding in pgvector, the database is computing cosine similarity between every stored vector and your query.
Transformer attentionThe Q·Kᵀ step in self-attention is a batch dot product — measuring how similar every token is to every other token.
Semantic search rankingHigher cosine similarity → more semantically similar documents → ranked higher in search results.

Exponential Moving Average (EMA) Essential

You're already using this in contrl for landmark smoothing. Understanding the formula tells you exactly how to tune alpha and why it behaves the way it does.

EMA Formula
EMA_t = α × value_t + (1 − α) × EMA_(t−1)
// α (alpha) = smoothing factor, range (0, 1)
// α = 0.1 → very smooth, slow to react (good for noisy sensors)
// α = 0.3 → balanced (contrl default)
// α = 0.9 → almost no smoothing, reacts immediately
// Higher α = more weight on current value = less smoothing
// The "exponential" part: older values decay by (1-α)^n each step

Intuition: at α=0.3, the current frame contributes 30% of the output. The previous EMA (which itself was a blend of all prior frames) contributes 70%. Each prior frame's influence decays geometrically — the frame 5 steps ago contributes roughly 0.7⁵ ≈ 17% of the EMA value.

Softmax Essential

Softmax converts a list of raw scores into a probability distribution (numbers that sum to 1.0). It appears in every LLM output — the model's "confidence" in each next token is a softmax over the entire vocabulary.

Softmax
softmax(xᵢ) = e^xᵢ / Σⱼ e^xⱼ
// Input: raw scores (logits) — any real numbers
// Output: probabilities that sum to exactly 1.0
// Example: scores = [2.0, 1.0, 0.1]
// e^2.0 = 7.39, e^1.0 = 2.72, e^0.1 = 1.10 → sum = 11.21
// softmax = [0.659, 0.242, 0.098] → sums to 1.0
// Temperature T scales the logits before softmax:
softmax_T(xᵢ) = e^(xᵢ/T) / Σⱼ e^(xⱼ/T)
// T=0.1 → near-deterministic (picks the highest score almost always)
// T=1.0 → standard softmax
// T=2.0 → flatter distribution (more creative/random)
// This is exactly what the "temperature" parameter does in getLLM()

When you set temperature: 0 in buffr's getLLM(), you're asking for near-deterministic selection — the model almost always picks the highest-probability token. At temperature: 1, it samples from the raw distribution. This is softmax with temperature scaling.

Scaled Dot-Product Attention Important

This is the core mathematical operation of every transformer — every LLM you call through buffr's API runs this billions of times per forward pass. You don't need to implement it, but understanding it explains: why context windows have limits, why longer prompts cost more, and what "attention" actually means.

Self-Attention
Attention(Q, K, V) = softmax(QKᵀ / √dₖ) × V
// Q = Query matrix (what am I looking for?)
// K = Key matrix (what does each token offer?)
// V = Value matrix (what information does each token contain?)
// dₖ = dimension of key vectors (square root stabilises gradients)
// Step 1: QKᵀ → attention scores matrix (how relevant is each token to each other?)
// Step 2: / √dₖ → scale to prevent vanishing gradients
// Step 3: softmax → convert scores to probabilities (attention weights)
// Step 4: × V → weighted sum of value vectors = context-aware output
// Why quadratic cost? QKᵀ is an (n×n) matrix for n tokens
// 1000 tokens → 1M operations. 100K tokens → 10B operations
// This is why context windows have limits and longer prompts cost more

Practical implication for buffr: the cost of an API call scales roughly quadratically with prompt length. A 4000-token prompt costs ~4× more compute than a 2000-token prompt. This is why token counting and prompt compression matter at scale.

Log Probability & Cross-Entropy Loss Important

When an LLM generates text, it's selecting tokens based on probability. Log probability appears in LLM API responses (logprobs), eval scoring, and helps you understand model confidence. Cross-entropy loss is how the model was trained — relevant when you get to fine-tuning.

Log Probability
log_prob = log(P(token))
// P("cat") = 0.8 → log_prob = log(0.8) ≈ -0.22
// P("xyz") = 0.01 → log_prob = log(0.01) ≈ -4.6
// Always negative (log of number < 1)
// Closer to 0 = higher confidence
// Perplexity = e^(-avg log_prob)
// Lower perplexity = model is less "surprised"
Cross-Entropy Loss
L = -Σᵢ yᵢ × log(p̂ᵢ)
// y = true label (one-hot vector)
// p̂ = model's predicted probability
// Measures: how surprised is the model by the truth?
// For LLMs: how wrong was the model's token prediction?
// Training minimises this across all tokens in the dataset
// Eval loss: lower = model learned the training distribution better

Vector Norms (L1 and L2) Important

The magnitude of a vector — used in cosine similarity, regularisation, and when comparing embeddings.

L2 Norm (Euclidean Distance)
‖a‖₂ = √(a₁² + a₂² + ... + aₙ²)
// "Straight-line" distance from origin
// Used in: cosine similarity denominator
// Normalised vector: a / ‖a‖₂
// Normalised vectors all live on unit sphere
// For normalised vectors: dot product = cosine similarity
L1 Norm (Manhattan Distance)
‖a‖₁ = |a₁| + |a₂| + ... + |aₙ|
// Sum of absolute values
// "Taxi cab" distance
// Less sensitive to outliers than L2
// Used in: sparse regularisation (L1 penalty)
// Encourages model weights to go to zero

Gradient Descent & Backpropagation Background

How models are trained. You don't implement this — PyTorch does it for you — but understanding the concept explains why training requires GPUs, why learning rate matters, and what "overfitting" means mechanically.

Gradient Descent Update Rule
θ_new = θ_old − η × ∇L(θ)
// θ (theta) = model weights (the numbers being learned)
// η (eta) = learning rate (how big a step to take)
// ∇L(θ) = gradient of the loss (which direction makes loss go up?)
// We move in the OPPOSITE direction of the gradient
// Repeat until loss stops decreasing (convergence)
// Too high η → overshoot minimum, training diverges
// Too low η → very slow convergence, risk of local minima
// Backprop computes ∇L(θ) efficiently using chain rule

When you fine-tune a model (Phase 4 of the curriculum), you run gradient descent on a small dataset to shift the model's weights toward the behaviour you want. Learning rate is the most important hyperparameter you'll tune.

Sliding Window Essential

A window of fixed size N that moves across a sequence, processing or aggregating elements within the window at each step. You built one in contrl for temporal smoothing. It also underpins rate limiting, context window management, and chunk overlap in RAG.

// Sliding window: add new element, remove old element → O(n)

// One add, one subtract — constant time regardless of k

DAG & Topological Sort Important

A Directed Acyclic Graph (DAG) where you need to process nodes in an order that respects all dependencies — no node is processed before everything it depends on. This is the algorithm that decides the execution order of an agentic workflow.

Kahn's Algorithm (topological sort)
// 1. Find all nodes with in-degree 0 (no dependencies) → add to queue
// 2. Dequeue a node, add to result order
// 3. For each neighbour, reduce in-degree by 1
// 4. If neighbour's in-degree hits 0, add to queue
// 5. Repeat until queue is empty
// 6. If result order has fewer nodes than the graph → cycle detected!
Complexity O(V + E)
// Cycle detection is free — a cycle means an agent workflow is impossible

Practical implication: when you build buffr's Phase 3 observation loop with chained tool calls, each step potentially depends on the output of a previous step. If you ever let the orchestrator plan a multi-step workflow, you're implicitly building a DAG and executing it in topological order. LangGraph makes this explicit.

Circular Buffer (Ring Buffer) Important

A fixed-size buffer that wraps around — when it fills up, new data overwrites the oldest data. The ideal structure for streaming sensor data: constant memory, O(1) read/write, always holds the last N samples.

Circular buffer mechanics
Write buffer[head % capacity] = value; head++
Read buffer[tail % capacity]; tail++
// % (modulo) is the key — it wraps the index back to 0 at capacity
// Fixed memory: capacity never grows regardless of how many frames arrive
// O(1) write and read
// Always contains the last `capacity` frames
// Example: capacity=30 (1 second of frames at 30fps)
// Frame 31 overwrites frame 1, frame 32 overwrites frame 2, etc.
// You always have the last 30 frames, using 30 slots of memory
Where it appearsWhat it's doing

Big-O Notation Essential

Big-O describes how an algorithm's time or space cost grows as the input size n grows. You don't need to derive it — you need to recognise the common classes and know which operations in your stack fall into each. This is what interviewers mean when they ask "what's the time complexity of that?"

// O(1) → 1 operation ← hash map lookup

🎯 Why is the attention mechanism O(n²) and why does that matter in practice? ▶
Self-attention computes a similarity score between every pair of tokens — for n tokens, that's n² comparisons. A 1,000-token prompt = 1M comparisons. A 100,000-token context = 10 billion comparisons. This is why longer context windows cost exponentially more and why models with 1M token context windows require architectural innovations like sparse attention or linear attention to be economically viable. For you as a product engineer: count tokens before sending them, truncate aggressively, and cache system prompts — every token in a long context costs quadratically.
Group 6 — String processing (in LLM output and prompt pipelines)

String Hashing & Tokenisation Algorithms Background

LLMs don't process raw strings — they process tokens produced by a tokenisation algorithm. Byte-Pair Encoding (BPE) is the algorithm behind most frontier models. Understanding it explains why "tokenisation" can produce surprising results for code, numbers, and non-English text.

Byte-Pair Encoding (BPE) — simplified
// 1. Start: vocabulary = all individual characters
// 2. Count: find the most frequent pair of adjacent tokens in the corpus
// 3. Merge: add the pair as a new token to the vocabulary
// 4. Replace: replace all occurrences of the pair with the new token
// 5. Repeat until vocabulary reaches target size (e.g. 50,000 tokens)
// "the cat sat" → frequent pairs: "th","he","ca","at" → "the","cat","sat"
// Common words become single tokens. Rare words split into subwords.
// "unbelievable" → ["un", "believ", "able"] (3 tokens, not 13 chars)
// "12345" → ["1", "2", "3", "4", "5"] (often 5 tokens — why math is hard)

Why this matters for buffr: numbers tokenise inefficiently — each digit is often its own token. A JSON object with many numeric values (session timestamps, scores) costs more tokens than you'd expect from the character count alone. When building the token counting exercise in Phase 4, use the actual tokeniser, not a character-count estimate.

Papers worth knowing (read the abstract + conclusion, not necessarily everything)
Paper · Free
Attention Is All You Need
Vaswani et al · Google Brain 2017
The paper that introduced the transformer architecture powering every LLM you use. Read the abstract, the attention formula (Section 3.2), and Figure 2. Skip the machine translation results. Understanding this formula explains why context windows cost quadratically.
Free · arXiv
Paper · Free
Retrieval-Augmented Generation (RAG)
Lewis et al · Meta AI 2020
The original RAG paper. Short and readable. Explains the core concept of combining parametric knowledge (model weights) with non-parametric retrieval (vector search). Read when you're building Phase 5 exercises — it contextualises everything you're building.
Free · arXiv
Paper · Free
ReAct: Reasoning + Acting in LLMs
Yao et al · Princeton 2022
The paper behind buffr's suggestedActions pattern and the ReAct prompt engineering technique. Shows how interleaving reasoning and tool calls dramatically improves agent accuracy. Read it when building the observation loop exercise in Phase 3.
Free · arXiv
Paper · Free
LoRA: Low-Rank Adaptation
Hu et al · Microsoft 2021
The technique behind efficient fine-tuning of large models. Instead of updating all weights (expensive), LoRA adds small trainable matrices. Read the abstract and Section 2 — enough to understand what "LoRA fine-tuning" means when you see it in Hugging Face tutorials.
