aipe is a spec workflow for AI-assisted development. 11 markdown templates that turn a one-line intent plus your project context into a filled, structured spec your coding agent can implement from — no extra runtime, no extra API keys.

How it works

One slash command per intent. Your agent does the rest.

You run /aipe:<type> <intent> in Claude Code or Codex. The plugin loads the matching template, reads your project context from .aipe/, and your agent fills the spec using its own model. The output is a structured markdown file ready to implement against.

01

Scaffold once

First run creates .aipe/project/context.md in your repo. You fill in stack, data model, file structure, constraints — the things your agent would otherwise guess.

02

Run a slash command

Pick a spec type — feature, debugging, refactor, audit, migration, performance, integration, plan, study, testing, user-stories. One slash command per type, tab-completable in both Claude Code and Codex CLI.

03

Get a filled spec

Agent reads template + context, composes the spec, saves to .aipe/specs/<type>/<slug>.md. You review. Then say "implement it" and the same agent builds against the spec.

$ /aipe:feature add dark mode toggle
→
# Feature spec ## Data model Settings: { theme: 'light' | 'dark' } ## Behaviour Tap → toggle → persist ## UI ... ✓ saved to .aipe/specs/features/dark-mode.md

11 spec types

One template per kind of work.

Each template is a plain markdown file in specs/. You can read them directly to see what each one produces. Adding a new spec type is a markdown edit, no build step.

/aipe:plan

Multi-phase project that spans sessions.

/aipe:feature

Building something new.

/aipe:debugging

A bug keeps coming back.

/aipe:study

Understand a codebase as a layered study guide — system design, DSA, AI engineering, ML.

/aipe:audit

Reviewing existing code before extending it.

/aipe:testing

Writing or improving tests.

/aipe:user-stories

Rewriting tasks in different personas.

/aipe:refactor

Restructuring without changing behaviour.

/aipe:migration

Changing schema, dependency, or storage.

/aipe:performance

Diagnosing speed or bundle issues.

/aipe:integration

Connecting an external service.

Install

Two commands. No CLI, no API keys.

Both plugins distribute via marketplace install. Same templates back both agents — edit a template, both surfaces update on the next plugin pull.

Claude Code

In any Claude Code session:

/plugin marketplace add rlynjb/aipe /plugin install aipe@rlynjb-aipe

Codex CLI

From your terminal:

codex plugin marketplace add rlynjb/aipe

Why aipe

The decisions that make this different.

aipe is deliberately small. It ships templates and slash commands — nothing else. The agent in your session does the work using its own model.

No external runtime

No CLI binary, no API keys, no auth, no service to deploy. The agent in your session does the work.

One source of truth

Both plugins load from the same specs/*.md files. Edit once, both surfaces update.

Per-project context

Your stack, file structure, and constraints live in .aipe/project/ — committed to the repo, edited as you go.

Markdown all the way

Templates are markdown. Generated specs are markdown. The state lives in files you own. No databases, no telemetry.

UPDATE mode is first-class

Re-running a command on a project with a spec diffs against the codebase and the template, patches only what drifted.

Free, MIT-licensed

Fork it, edit it, ship your own variant. The repo is the product.
