🎯 Why did you abstract your LLM provider instead of calling the Anthropic SDK directly? ▶
Because locking business logic to a vendor is a design smell. With a factory function, you can add a new provider in one place, A/B test models without touching chains, and fall back gracefully if a provider is down — without modifying the code that actually does work.

🎯 When would you use few-shot prompting instead of zero-shot? ▶
When output format consistency keeps failing zero-shot. Two or three examples in the prompt dramatically increase reliability for unusual JSON shapes or non-standard classification labels. The cost is prompt tokens — for high-volume endpoints, few-shot can double your token spend.
Analyze · Prompt Autopsy Find the 4 problems in this system prompt buffr · Phase 1 ▶

This is a real-looking system prompt for buffr's session summariser. Before revealing the analysis, study it and write down every problem you can find. Look for: reliability issues, missing constraints, ambiguous instructions, format problems.

You are an AI assistant helping developers track their work sessions. When the user gives you a list of their activities, please summarize what they did and provide some helpful bullet points. Try to be concise but also detailed enough that the user can understand what happened. The summary should be relevant. Return your response as JSON if possible.
Your task: Identify every problem before expanding. Write them down first — this is the critical thinking rep. Aim for at least 4 distinct issues.
1
No schema specified. "Return your response as JSON if possible" guarantees inconsistency. The model has no idea what keys to use. You'll get {"summary": "..."} on one call, {"goal": "...", "points": [...]} on the next. Every chain needs an exact JSON schema in the system prompt with field names, types, and an example.
2
"If possible" is a soft constraint. LLMs interpret hedged instructions loosely. "Return JSON if possible" means the model will return prose whenever it feels uncertain. Replace with: "Return ONLY valid JSON. No markdown fences. No explanation. No prefix text."
3
Contradictory length instructions. "Be concise but also detailed enough" gives the model no guidance — these pull in opposite directions. Specify the actual constraint: "Return 1 goal sentence (max 15 words) and 3–6 bullet points (max 10 words each)."
4
No persona or domain anchor. "AI assistant helping developers" is vague. The model doesn't know it should be technical, that "activities" are GitHub commits and tasks, or that the output will be shown to a developer. Anchor the persona: "You are a senior software engineering assistant. The user is a developer. Activities are GitHub events, completed tasks, and manual notes."
5
No failure instruction. What should the model do if the activity list is empty, or contains only one item? Without explicit handling, the model invents content. Add: "If the activity list is empty, return {"goal": "No activity recorded", "bullets": []}."
Decide · Tradeoff Should you add few-shot examples to the dev scanner prompt? buffr · Phase 1 ▶
buffr's dev scanner sends a prompt with 8,000 tokens of industry standards + ~2,000 tokens of project metadata. The current zero-shot output is good but occasionally mis-classifies the detected stack (e.g. marks a Next.js project as "React only"). Adding 3 few-shot examples of correct stack detection would cost an extra ~1,200 tokens per call. The scanner runs ~8 times per user per month. You have 200 users.
Option A
Add the few-shot examples. Better accuracy justifies the token cost.
Option B
Don't add examples. Fix the zero-shot prompt wording instead — it's cheaper and reversible.
The honest answer: it depends, and you need to measure first
Before choosing, ask: Is the classification error happening because the model doesn't understand the task (→ few-shot helps), or because the system prompt instructions are ambiguous (→ prompt fix helps)?

The cost math: 200 users × 8 scans × 1,200 extra tokens = 1.92M tokens/month extra. At $3/M input, that's ~$5.76/month. Negligible at this scale.

But cost isn't the real question. The right sequence is: (1) build an eval harness with 10 mis-classified projects, (2) try fixing the zero-shot prompt wording first — it's free and fast, (3) if that doesn't hit your quality target, add the few-shot examples. Never add tokens before measuring whether they actually improve accuracy on your specific failure cases. Few-shot examples that don't match your failure patterns will cost tokens without fixing the problem.

2.1 Serverless vs Traditional

Key implication for AI products: LLM calls can take 5–30 seconds. Solutions: streaming (return tokens immediately) or queue/job pattern (async processing).

🎯 What are the limitations of serverless for AI applications? ▶
Two main limitations: timeout limits and no persistent state. For timeouts, streaming is the primary solution — start returning tokens immediately so the function doesn't time out waiting. For persistent state you need external storage. A secondary limitation is cold starts — mitigated by keeping bundles small and using dynamic imports so unused SDK code isn't loaded.

2.3 Storage Patterns & Race Conditions

PatternWhat it isWhen to use
Key-value storeSimple map of key → JSON blobPrototypes, per-user config, small datasets < 1000 items
Relational (Postgres)Tables, indexes, SQL queries, joinsWhen you need to filter/sort/search across records
List + filter in memorybuffr's "query" strategy: fetch all, filter in JSOnly works at small scale — 500 records max
Index patternSeparate index key tracking which items belong to a setFirst migration step before moving to a real database

The TOCTOU race condition — a real bug encountered in buffr:

BROKEN (Promise.all):
  Delete A: read [A,B,C] → remove A → write [B,C]
  Delete B: read [A,B,C] → remove B → write [A,C]  ← stale read!
  Result: A is back. Last write wins.

FIXED (sequential):
  Delete A: read [A,B,C] → remove A → write [B,C]
  Delete B: read [B,C]   → remove B → write [C]    ← reads fresh state
🎯 When would you migrate buffr from Netlify Blobs to Postgres? ▶
When queries become the bottleneck — filtering sessions by date range, searching prompt text, or joining sessions with project data. The tell-tale sign is list-and-filter-in-memory becoming visibly slow, usually around 500–1000 records. I'd migrate to Supabase Postgres, add an index on projectId and createdAt, and keep the storage module interface unchanged so chain code doesn't need to change.
Trace the Bug Walk the TOCTOU failure frame by frame buffr · Storage ▶

A user has 3 completed actions: [A, B, C]. They click "clear all" which calls Promise.all([deleteAction('A'), deleteAction('B'), deleteAction('C')]). After it resolves, action A is still in the list. Trace exactly why before expanding.

→
T=0ms: Promise.all fires all 3 delete calls simultaneously. All three execute store.get('actions') before any write completes.
→
T=1ms (deleteA reads): reads [A, B, C]. Filters to [B, C]. Prepares to write.
→
T=1ms (deleteB reads): also reads [A, B, C] — same stale snapshot, because deleteA hasn't written yet. Filters to [A, C]. Prepares to write.
→
T=2ms (deleteA writes): writes [B, C]. Storage now contains [B, C].
→
T=3ms (deleteB writes): writes [A, C] — its stale read. Storage is now [A, C]. deleteA's write is overwritten. A is back.
→
T=4ms (deleteC writes): also read [A, B, C] originally. Writes [A, B]. Final state: [A, B]. Both B and C are also back now.
Root cause: Read-modify-write is not atomic in blob storage. Concurrent reads all see pre-write state. Each write only removes the item it targeted, overwriting whatever the previous write stored. The fix is sequential execution: for...of loop instead of Promise.all, so each read sees the result of the previous write. This trades parallelism for correctness — the right tradeoff when operations share mutable state.
Analyze · Performance Find the 3 complexity problems in this storage function buffr · DSA ▶

This is a plausible implementation of listSessionsByProject() in buffr. Study it and identify every performance issue before revealing the analysis. Ask yourself: what is n? What is the complexity of each operation? What breaks at scale?

async function listSessionsByProject(projectId: string) { const allKeys = await store.list() // fetch all keys const sessions = [] for (const key of allKeys.keys) { // loop every key const session = await store.get(key.name) // N blob reads (sequential!) if (session) { const parsed = JSON.parse(session) if (parsed.projectId === projectId) { // filter in JS sessions.push(parsed) } } } return sessions.sort( // sort after filtering (a, b) => new Date(b.createdAt) - new Date(a.createdAt) ) }
Your task: Identify every performance issue. Estimate: at 10,000 total sessions across all users, how many blob reads does this function make to find one user's 50 sessions?
1
O(n) sequential blob reads. The for...of loop awaits each store.get() before fetching the next. At 10,000 sessions, this makes 10,000 sequential HTTP calls, one at a time. Even at 5ms each, that's 50 seconds. This alone is a fatal performance bug. Fix: Promise.all(keys.map(k => store.get(k.name))) fetches in parallel — reduces wall time from O(n × latency) to O(latency) with concurrency.
2
O(n) full scan regardless of projectId. All 10,000 sessions are fetched and deserialised to find one user's 50. There's no index. Fix: maintain a project:{id}:sessions index key that stores only session IDs for a given project. Then fetch only those IDs — O(k) reads where k = sessions for that project, not total sessions.
3
Redundant sort on every call. Array.sort() is O(n log n) where n = returned sessions. If you sort at write time (insert sessions into the index in timestamp order), reads are already sorted — O(1) for the sort step. Minor optimisation, but reveals a write-vs-read-time tradeoff worth knowing.
4
JSON.parse inside a tight loop. Deserialising 10,000 JSON blobs is CPU-intensive. At scale this saturates the serverless function's CPU budget and triggers throttling. If you had an index, you'd only deserialise the sessions you actually need.

3.1 The Tool Registry Pattern

buffr's tool registry is a hand-rolled version of the pattern behind all agentic AI — MCP, OpenAI function calling, LangChain tools. The concept is always the same: define capabilities, register at startup, let the model suggest which to call, execute in your code.

ConceptHow it works in buffr
Tool definitionname, description, inputSchema (JSON Schema), execute function. The description is what the LLM reads to decide whether to call it.
Tool registryA global Map populated at cold start. O(1) lookup by name. New tools registered via registerTool() — the router doesn't change.
suggestedActionsLLM-suggested tool names + inputs. Your backend validates and executes them.
Server-side executionStage 2 {{tool:...}} resolution runs server-side. GitHub tokens never reach the browser.
MCP equivalenceAnthropic's MCP formalises this exact pattern. buffr's registry could be wrapped as an MCP server with minimal changes.
🎯 Explain the difference between tool use and RAG. When would you use each? ▶
RAG pre-fetches data and injects it into the prompt before the LLM call — the model sees the data but can't decide whether to fetch it. Tool use lets the model decide at inference time what actions to take — it's dynamic and can chain. Use RAG when you always need context (e.g. always include user's recent sessions). Use tools when the action depends on the model's reasoning. buffr uses both: {{tool:...}} tokens are RAG; suggestedActions are tool use.

Decide · Architecture Should tool results wait for the LLM, or run in parallel? buffr · Performance ▶
A user runs a prompt with two tool tokens: {{tool:github_list_issues}} and {{tool:notion_list_tasks}}. Currently buffr resolves these sequentially: GitHub first, then Notion, then sends the resolved prompt to the LLM. GitHub takes ~300ms, Notion takes ~400ms. Total pre-LLM latency: 700ms. A teammate suggests switching to Promise.all to run both simultaneously: total pre-LLM latency drops to ~400ms.
Option A — Sequential (current)
Run GitHub, wait for result, then run Notion, wait, then call LLM. Safe. 700ms.
Option B — Parallel Promise.all
Run both tool calls concurrently, wait for both, then call LLM. 300ms faster. But — does anything break?
Parallel is correct here — with one condition
For independent read-only tool calls like fetching GitHub issues and Notion tasks, Promise.all is the right call. These tools don't depend on each other's output, don't write shared state, and the 300ms saving is real and compounding at scale.

The condition: only parallelise when tools are truly independent. The dangerous case is when tool B's input should be derived from tool A's output — e.g. {{tool:github_get_pr}} followed by {{tool:github_get_diff?pr_number={result_of_above}}. Those must stay sequential.

Contrast with the TOCTOU bug in storage: that was concurrent writes to shared mutable state — fundamentally different. Promise.all is dangerous for writes, safe for independent reads. Knowing which applies is the critical thinking skill here.

🎯 How do you know if your AI feature is working correctly? ▶

Your task: List every flaw in this judge prompt before revealing the analysis. Consider: what makes a score of 5 vs 4 vs 3? Can you reproduce the same score twice? What does "be fair and balanced" actually mean to a model?
1
No rubric — the scoring scale is undefined. "5 = excellent, 1 = poor" gives the model no way to distinguish a 3 from a 4. A good judge prompt defines each score level explicitly: "5 = covers all activities accurately with a coherent goal sentence and 3–6 specific bullets. 4 = covers most activities, minor omission. 3 = goal is correct but bullets are vague..." Without a rubric, two identical outputs get different scores on different calls.
2
No reference output or criteria. The judge doesn't know what a "good" summary of these specific activities looks like. It can't tell if "maintenance tasks" is the right abstraction or a wrong one. Good evals include the expected output (or the rubric criteria) so the judge measures against something concrete, not its own general knowledge of "good summaries."
3
"Be fair and balanced" is meaningless instruction. This is filler that adds tokens without adding precision. Models don't have a "biased" mode that this instruction disables. Replace with specific criteria: "Do not penalise creative phrasing if the meaning is correct. Do penalise missing activities — every item in the input must be represented in the output."
4

Your task: This will massively over-count. Find every specific problem. How many times does repCount++ fire during a single 2-second push-up at 30fps where the elbow stays below 90° for 15 frames at the bottom?
1
No state machine — counts every frame below threshold, not every rep. If the elbow stays below 90° for 15 frames, repCount increments 15 times. One rep = +15. This is the root cause of the over-count. A rep is a transition event (cross threshold going down, then cross going up), not a level condition. The fix is a state machine: only count when transitioning from a "down" state back to "up."
2
No EMA smoothing — sensor noise causes phantom threshold crossings. If the raw angle oscillates around 90° due to jitter (e.g. 89°, 91°, 88°, 92° over 4 consecutive frames), the counter fires twice per oscillation. At the bottom of a rep, where angles are near the threshold, this noise creates false transitions. Apply EMA (alpha ≈ 0.3) before the threshold check to smooth the signal.
3
No visibility check — occluded landmarks produce garbage angles. When the elbow is partially out of frame or lighting is poor, MediaPipe assigns low visibility scores but still outputs coordinates. Those coordinates are unreliable, producing angles anywhere from 0° to 180°. Any angle calculation on a landmark with visibility < 0.6 should be skipped entirely — no state update, no count.
4
No temporal confirmation — a single noisy frame triggers a count. Even with EMA, a large sensor spike can briefly cross the threshold for 1–2 frames. Requiring 3 consecutive frames below the threshold before transitioning to "down" state eliminates single-frame false positives without meaningfully delaying detection.
5
Only left-side landmarks used — asymmetric movement breaks detection. landmarks[11] is the left shoulder, landmarks[13] the left elbow, landmarks[15] the left wrist. If the user's left arm is partially occluded (facing right camera), all counts fail. Bilateral averaging — compute both left and right angles, use the higher-visibility side — gives robust detection for any camera orientation.

Dot Product & Cosine Similarity Essential

The single most important formula in AI product engineering. It powers similarity search, embeddings, attention, and your joint angle calculations in contrl — all the same underlying operation.

Dot Product
a · b = a₁b₁ + a₂b₂ + ... + aₙbₙ
// Sum of element-wise products
// Result: a single number (scalar)
// Large positive = vectors point same way
// Near zero = perpendicular (unrelated)
// Negative = opposite directions
Cosine Similarity
cos(θ) = (a · b) / (‖a‖ × ‖b‖)
// Normalised dot product → range [-1, 1]
// 1.0 = identical meaning
// 0.0 = unrelated
// -1.0 = opposite
// ‖a‖ = magnitude = √(a₁²+ a₂²+ ...)

Exponential Moving Average (EMA) Essential

You're already using this in contrl for landmark smoothing. Understanding the formula tells you exactly how to tune alpha and why it behaves the way it does.

EMA Formula
EMA_t = α × value_t + (1 − α) × EMA_(t−1)
// α (alpha) = smoothing factor, range (0, 1)
// α = 0.1 → very smooth, slow to react (good for noisy sensors)
// α = 0.3 → balanced (contrl default)
// α = 0.9 → almost no smoothing, reacts immediately
// Higher α = more weight on current value = less smoothing
// The "exponential" part: older values decay by (1-α)^n each step

Intuition: at α=0.3, the current frame contributes 30% of the output. The previous EMA (which itself was a blend of all prior frames) contributes 70%. Each prior frame's influence decays geometrically — the frame 5 steps ago contributes roughly 0.7⁵ ≈ 17% of the EMA value.

Softmax Essential

Softmax converts a list of raw scores into a probability distribution (numbers that sum to 1.0). It appears in every LLM output — the model's "confidence" in each next token is a softmax over the entire vocabulary.

Softmax
softmax(xᵢ) = e^xᵢ / Σⱼ e^xⱼ
// Input: raw scores (logits) — any real numbers
// Output: probabilities that sum to exactly 1.0
// Example: scores = [2.0, 1.0, 0.1]
// e^2.0 = 7.39, e^1.0 = 2.72, e^0.1 = 1.10 → sum = 11.21
// softmax = [0.659, 0.242, 0.098] → sums to 1.0
// Temperature T scales the logits before softmax:
softmax_T(xᵢ) = e^(xᵢ/T) / Σⱼ e^(xⱼ/T)
// T=0.1 → near-deterministic (picks the highest score almost always)
// T=1.0 → standard softmax
// T=2.0 → flatter distribution (more creative/random)
// This is exactly what the "temperature" parameter does in getLLM()

When you set temperature: 0 in buffr's getLLM(), you're asking for near-deterministic selection — the model almost always picks the highest-probability token. At temperature: 1, it samples from the raw distribution. This is softmax with temperature scaling.

Tier 2 — You need this for the ML track & deeper LLM understanding

Scaled Dot-Product Attention Important

This is the core mathematical operation of every transformer — every LLM you call through buffr's API runs this billions of times per forward pass. You don't need to implement it, but understanding it explains: why context windows have limits, why longer prompts cost more, and what "attention" actually means.

Self-Attention
Attention(Q, K, V) = softmax(QKᵀ / √dₖ) × V
// Q = Query matrix (what am I looking for?)
// K = Key matrix (what does each token offer?)
// V = Value matrix (what information does each token contain?)
// dₖ = dimension of key vectors (square root stabilises gradients)
// Step 1: QKᵀ → attention scores matrix (how relevant is each token to each other?)
// Step 2: / √dₖ → scale to prevent vanishing gradients
// Step 3: softmax → convert scores to probabilities (attention weights)
// Step 4: × V → weighted sum of value vectors = context-aware output
// Why quadratic cost? QKᵀ is an (n×n) matrix for n tokens
// 1000 tokens → 1M operations. 100K tokens → 10B operations
// This is why context windows have limits and longer prompts cost more

Practical implication for buffr: the cost of an API call scales roughly quadratically with prompt length. A 4000-token prompt costs ~4× more compute than a 2000-token prompt. This is why token counting and prompt compression matter at scale.

Log Probability & Cross-Entropy Loss Important

When an LLM generates text, it's selecting tokens based on probability. Log probability appears in LLM API responses (logprobs), eval scoring, and helps you understand model confidence. Cross-entropy loss is how the model was trained — relevant when you get to fine-tuning.

Log Probability
log_prob = log(P(token))
// P("cat") = 0.8 → log_prob = log(0.8) ≈ -0.22
// P("xyz") = 0.01 → log_prob = log(0.01) ≈ -4.6
// Always negative (log of number < 1)
// Closer to 0 = higher confidence
// Perplexity = e^(-avg log_prob)
// Lower perplexity = model is less "surprised"
Cross-Entropy Loss
L = -Σᵢ yᵢ × log(p̂ᵢ)
// y = true label (one-hot vector)
// p̂ = model's predicted probability
// Measures: how surprised is the model by the truth?
// For LLMs: how wrong was the model's token prediction?
// Training minimises this across all tokens in the dataset
// Eval loss: lower = model learned the training distribution better

Gradient Descent & Backpropagation Background

How models are trained. You don't implement this — PyTorch does it for you — but understanding the concept explains why training requires GPUs, why learning rate matters, and what "overfitting" means mechanically.

Gradient Descent Update Rule
θ_new = θ_old − η × ∇L(θ)
// θ (theta) = model weights (the numbers being learned)
// η (eta) = learning rate (how big a step to take)
// ∇L(θ) = gradient of the loss (which direction makes loss go up?)
// We move in the OPPOSITE direction of the gradient
// Repeat until loss stops decreasing (convergence)
// Too high η → overshoot minimum, training diverges
// Too low η → very slow convergence, risk of local minima
// Backprop computes ∇L(θ) efficiently using chain rule

When you fine-tune a model (Phase 4 of the curriculum), you run gradient descent on a small dataset to shift the model's weights toward the behaviour you want. Learning rate is the most important hyperparameter you'll tune.

Information Theory: Entropy & KL Divergence Deep Dive

These appear in eval metrics, fine-tuning loss functions, and are essential vocabulary when reading ML papers. Understand the intuition — the formula comes later.

Shannon Entropy
H(p) = -Σᵢ p(xᵢ) × log₂ p(xᵢ)
// Measures: how uncertain is a probability distribution?

// High entropy LLM output = creative/random
// Low entropy LLM output = deterministic/confident

// Measures: how different is distribution q from distribution p?
// KL = 0 → distributions are identical
// Not symmetric: KL(p‖q) ≠ KL(q‖p)

Sliding Window Essential

A window of fixed size N that moves across a sequence, processing or aggregating elements within the window at each step. You built one in contrl for temporal smoothing. It also underpins rate limiting, context window management, and chunk overlap in RAG.

// Sliding window: add new element, remove old element → O(n)

// One add, one subtract — constant time regardless of k

A graph is a set of nodes (vertices) connected by edges. Unlike trees, graphs can have cycles and multiple paths between nodes. Two traversal algorithms — BFS and DFS — cover the vast majority of graph problems you'll encounter as an AI engineer.

DAG & Topological Sort Important

A Directed Acyclic Graph (DAG) where you need to process nodes in an order that respects all dependencies — no node is processed before everything it depends on. This is the algorithm that decides the execution order of an agentic workflow.

Kahn's Algorithm (topological sort)
// 1. Find all nodes with in-degree 0 (no dependencies) → add to queue
// 2. Dequeue a node, add to result order
// 3. For each neighbour, reduce in-degree by 1
// 4. If neighbour's in-degree hits 0, add to queue
// 5. Repeat until queue is empty
// 6. If result order has fewer nodes than the graph → cycle detected!
Complexity O(V + E)
// Cycle detection is free — a cycle means an agent workflow is impossible

Practical implication: when you build buffr's Phase 3 observation loop with chained tool calls, each step potentially depends on the output of a previous step. If you ever let the orchestrator plan a multi-step workflow, you're implicitly building a DAG and executing it in topological order. LangGraph makes this explicit.

Group 4 — Sequences & Buffers (real-time data in contrl)

Circular Buffer (Ring Buffer) Important

A fixed-size buffer that wraps around — when it fills up, new data overwrites the oldest data. The ideal structure for streaming sensor data: constant memory, O(1) read/write, always holds the last N samples.

Circular buffer mechanics
Write buffer[head % capacity] = value; head++
Read buffer[tail % capacity]; tail++
// % (modulo) is the key — it wraps the index back to 0 at capacity
// Fixed memory: capacity never grows regardless of how many frames arrive
// O(1) write and read
// Always contains the last `capacity` frames
// Example: capacity=30 (1 second of frames at 30fps)
// Frame 31 overwrites frame 1, frame 32 overwrites frame 2, etc.
// You always have the last 30 frames, using 30 slots of memory
Where it appearsWhat it's doing
contrl frame smoothingInstead of keeping an ever-growing array of landmark frames, a circular buffer of size N holds only the last N frames for EMA and phase detection. Memory stays constant at 30fps × session hours.
LLM token streaming bufferWhen streaming tokens from the LLM to the browser, a ring buffer in the server-side stream accumulates partial chunks and flushes complete JSON objects — avoids accumulating unbounded memory.
MediaPipe frame queueUnder the hood, MediaPipe's video processing uses a ring buffer between the camera feed and the inference engine. Frames that arrive faster than inference can process are dropped (overwritten) rather than queued indefinitely.

Priority Queue (Min/Max Heap) Background

A queue where elements are dequeued in priority order rather than arrival order. O(log n) insert and extract-min/max. Relevant to understanding how vector search engines rank results and how job schedulers work.

Heap complexity
Insert O(log n) // "bubble up" to maintain heap property
Extract-min O(log n) // remove root, "bubble down" replacement
Peek-min O(1) // root is always the minimum
// Min-heap: parent always ≤ children
// Max-heap: parent always ≥ children
// Top-k results from ANN search: keep a min-heap of size k
// When new candidate arrives: if similarity > heap.min, swap in
// After scanning all candidates: heap contains the top-k results
Where it appearsWhat it's doing

Big-O Notation Essential

Big-O describes how an algorithm's time or space cost grows as the input size n grows. You don't need to derive it — you need to recognise the common classes and know which operations in your stack fall into each. This is what interviewers mean when they ask "what's the time complexity of that?"

🎯 Why is the attention mechanism O(n²) and why does that matter in practice? ▶
Self-attention computes a similarity score between every pair of tokens — for n tokens, that's n² comparisons. A 1,000-token prompt = 1M comparisons. A 100,000-token context = 10 billion comparisons. This is why longer context windows cost exponentially more and why models with 1M token context windows require architectural innovations like sparse attention or linear attention to be economically viable. For you as a product engineer: count tokens before sending them, truncate aggressively, and cache system prompts — every token in a long context costs quadratically.
Group 6 — String processing (in LLM output and prompt pipelines)

String Hashing & Tokenisation Algorithms Background

LLMs don't process raw strings — they process tokens produced by a tokenisation algorithm. Byte-Pair Encoding (BPE) is the algorithm behind most frontier models. Understanding it explains why "tokenisation" can produce surprising results for code, numbers, and non-English text.

Byte-Pair Encoding (BPE) — simplified
// 1. Start: vocabulary = all individual characters
// 2. Count: find the most frequent pair of adjacent tokens in the corpus
// 3. Merge: add the pair as a new token to the vocabulary
// 4. Replace: replace all occurrences of the pair with the new token
// 5. Repeat until vocabulary reaches target size (e.g. 50,000 tokens)
// "the cat sat" → frequent pairs: "th","he","ca","at" → "the","cat","sat"
// Common words become single tokens. Rare words split into subwords.
// "unbelievable" → ["un", "believ", "able"] (3 tokens, not 13 chars)
// "12345" → ["1", "2", "3", "4", "5"] (often 5 tokens — why math is hard)

Why this matters for buffr: numbers tokenise inefficiently — each digit is often its own token. A JSON object with many numeric values (session timestamps, scores) costs more tokens than you'd expect from the character count alone. When building the token counting exercise in Phase 4, use the actual tokeniser, not a character-count estimate.

Papers worth knowing (read the abstract + conclusion, not necessarily everything)
Paper · Free
Attention Is All You Need
Vaswani et al · Google Brain 2017
The paper that introduced the transformer architecture powering every LLM you use. Read the abstract, the attention formula (Section 3.2), and Figure 2. Skip the machine translation results. Understanding this formula explains why context windows cost quadratically.

Paper · Free
Retrieval-Augmented Generation (RAG)
Lewis et al · Meta AI 2020
The original RAG paper. Short and readable. Explains the core concept of combining parametric knowledge (model weights) with non-parametric retrieval (vector search). Read when you're building Phase 5 exercises — it contextualises everything you're building.
Free · arXiv
Paper · Free
ReAct: Reasoning + Acting in LLMs
Yao et al · Princeton 2022
The paper behind buffr's suggestedActions pattern and the ReAct prompt engineering technique. Shows how interleaving reasoning and tool calls dramatically improves agent accuracy. Read it when building the observation loop exercise in Phase 3.
Free · arXiv
Paper · Free
LoRA: Low-Rank Adaptation
Hu et al · Microsoft 2021
The technique behind efficient fine-tuning of large models. Instead of updating all weights (expensive), LoRA adds small trainable matrices. Read the abstract and Section 2 — enough to understand what "LoRA fine-tuning" means when you see it in Hugging Face tutorials.
