For multi-session work, prompt engineering is really spec writing. Better spec = fewer bugs, less context re-established each session. This is what the .dev/ folder in buffr is for.

02 — Detail vs high-level

When to go deep vs stay broad

Use detail when

Complex or branching logic

Specific structure needed

Fitting into an existing codebase

AI has guessed wrong before

Stay high-level when

Exploring or prototyping

Task is well understood

You want AI's best approach

Creative latitude helps

More detail = less guessing. Less detail = better solutions you didn't think of.

03 — Feature implementation order

System → behaviour → UI

Never start with UI — AI infers logic from how things look and guesses on edge cases. Lead with system design so UI becomes a consequence of the data.
1

System design

What data exists, where it lives, what changes when the feature runs

2

Behaviour

Interaction flow — all three paths (happy, unhappy, weird)

3

UI last

Visual treatment, layout, spacing — constrained by what system and behaviour already defined

Feature prompt structure

## Data model [what exists, what shape it's in] ## What changes [what this feature reads, writes, or mutates] ## Behaviour [interaction flow — happy, unhappy, weird paths] ## UI [visual treatment — only after above is locked] ## Constraints [must do X / must not do Y]

For Notion as DB: always define the page/block schema upfront — AI will invent one mid-implementation if you don't.

04 — Two-layer prompt structure

Intent + constraints

1 — Intent

What you want and why (1–3 sentences)

2 — Constraints

- Must do X - Must not do Y - Edge case: if Z, then...
Pseudocode works best when you have a specific algorithm in mind. For UI/UX flows, use interaction flow prompting instead.

05 — The three user paths

Happy / unhappy / weird

Happy path

User does everything perfectly, once — AI defaults to this

Unhappy path

Network fails, data missing, double-submit, permissions denied, session expired

Weird path

Technically valid but unintended — 1000 items in a list, 3-day idle session, emoji in a number field

Label these sections explicitly in your prompt — the model shifts its thinking accordingly.

06 — Interaction flow template

Narrate the full user experience including failure

User opens [screen] ([state]) → if [condition]: [behaviour] → if [other condition]: [behaviour] User taps [element] → if [state A]: [action] → if [state B]: [action] → if [edge case]: [decision] User leaves / returns → [persistence behaviour] → [reset behaviour]

07 — Always describe these three states

What AI skips by default

Empty / zero state No data yet — what does the screen show?
Error / edge state Action fails, is slow, or is repeated
Re-entry behaviour Refresh, next session, back button
Naming all three catches ~70% of edge case bugs before you run the code.
